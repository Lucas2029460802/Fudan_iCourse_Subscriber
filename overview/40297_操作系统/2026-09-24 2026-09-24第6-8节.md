### 进程描述符与进程控制块

进程是程序的一次执行，是一个动态实体。与静态的程序不同，进程有创建、运行、阻塞和终止等完整的生命周期。操作系统要管理系统中大量并发的进程，就必须为每一个进程维护一组关键信息，这组信息集中存放在一个数据结构中，称为**进程控制块（Process Control Block, PCB）**，也可以称为**进程描述符（Process Descriptor）**。

PCB 是操作系统感知和管理进程的唯一依据。系统中有多个进程同时存在时，操作系统会把所有进程的 PCB 组织在一起，形成一张**进程表（Process Table）**。进程表本质上是一个结构数组，每个表项对应一个进程的 PCB。每个进程拥有一个全局唯一的标识符，即进程 ID，或称为 PID。通过 PID 可以在进程表中定位到对应进程的 PCB，从而获取该进程的完整管理信息。

从内容上看，PCB 中保存的信息通常可以划分为三大类。

第一类是**进程标识信息（Process Identification）**。其中最重要的是 PID，它是进程在系统内的唯一数字标识，是操作系统调度和管理进程的核心索引。此外还包括父进程 ID（PPID），用于标识创建当前进程的父进程，从而构建系统的进程树结构，维护父子进程之间的生命周期关联。用户 ID（UID）和组 ID（GID）则决定进程属于哪个用户以及它对系统资源的访问权限边界。进程标识信息较为简单，但它是操作系统识别进程、判断归属与权限的基础。

第二类是**处理器状态信息（Processor State Information）**。在多道程序环境下，一个进程运行一段时间后可能被剥夺 CPU，之后又要能够从被打断的位置继续执行。要做到这一点，操作系统必须在进程切换时保存 CPU 的寄存器组和执行状态，并在恢复执行前把这些状态重新装入 CPU。PCB 中正是保存了这样一份处理器状态信息的副本。这些信息包括程序计数器 PC、通用寄存器、状态寄存器、栈指针等。正是通过对处理器状态的保存与恢复，操作系统才实现了 CPU 的虚拟化，即把一个物理 CPU 在时间上复用给多个进程，造成多个进程“同时运行”的假象。

第三类是**进程控制信息（Process Control Information）**。这一类信息较为繁杂，凡是不属于前两类的进程管理信息，通常都归入其中。具体来说，它包括以下内容：

- 与调度和状态相关的信息。操作系统进行短程调度时，需要知道进程当前状态、调度优先级、已等待时间、上一次运行时间等。如果多个就绪进程优先级相同，调度器还需要依据等待时间等辅助信息决定选择哪一个。对于处于阻塞态的进程，还要记录它正在等待的事件，以便事件发生后能够将其唤醒。
- 与内存管理相关的信息。包括指向页表或段表的指针，这些表用于描述分配给该进程的虚拟内存。内存管理所需的具体数据结构取决于系统采用的内存管理方案。
- 资源拥有信息。例如进程打开的文件描述符表指针、占用的 I/O 资源等。
- 记账信息。记录处理器或其他资源的使用历史，可用于计费、性能分析和调度决策。

进程映像在内存中的位置信息也与内存管理方案密切相关。如果进程映像以连续内存块的形式存放，操作系统只需要记录该进程在物理内存中的起始地址 $B$ 和长度 $L$，则该进程占据的物理地址范围就是从 $B$ 到 $B+L-1$。如果进程映像由一组不连续存储的页面或段组成，那么进程表或内存管理数据结构中就必须记录每一个页面或段的位置，此时通常需要页表或段表来维护虚拟地址到物理地址的映射关系。

从进程映像的内部结构来看，一个进程通常包括代码段（Text Segment）、已初始化数据段（Data Segment）、未初始化数据段（BSS Segment）、堆（Heap）和栈（Stack）。代码段保存可执行指令，数据段保存全局变量和静态变量，堆用于显式请求的动态内存分配，而栈用于函数调用过程中的局部变量、函数参数和返回地址。PCB 中需要维护一个程序计数器，指出进程当前要执行的下一条指令的位置。此外，进程创建时默认会打开三个文件描述符：标准输入、标准输出和标准错误输出。标准输入通常对应键盘，标准输出和标准错误输出通常对应显示终端。

PCB 的组织方式主要有两种。**链接方式**是把具有同一状态的 PCB 通过链接字链接成队列，例如就绪队列、阻塞队列和空闲队列。**索引方式**则是系统根据进程状态创建若干索引表，例如就绪索引表、阻塞索引表，每个索引表项指向相应状态的某个 PCB。无论采用哪种组织方式，核心目的都是使操作系统能够高效地查找和管理不同状态的进程。

### 进程控制：创建与终止

进程控制主要涉及进程的创建和终止。

进程创建时，操作系统需要完成一系列工作。首先，为进程分配一个唯一的进程标识符 PID。其次，为进程分配地址空间，包括用户地址空间中的程序、数据、栈和堆。如果父进程希望与子进程共享某一块内存区域，还需要在创建时设置相应的链接，使子进程能够访问该共享区域，从而支持父子进程之间的通信和数据交换。然后，为进程控制块分配空间并对其进行初始化，设置 PCB 中的各个属性值，并建立合适的链接。此外，还需要完成必要的审计信息初始化等工作。

从磁盘上的程序到内存中的进程，转换过程大致可以分为五个步骤：第一，将代码和静态数据从磁盘上的可执行文件加载到进程的地址空间中；第二，为栈分配内存空间，栈中保存局部变量、函数参数和返回地址，函数调用时系统隐式地为每次调用分配栈帧；第三，为堆分配内存空间，堆用于显式请求的动态内存分配，例如 C 语言中的 `malloc` 或 C++ 中的 `new`；第四，执行与 I/O 相关的初始化工作，例如在 UNIX 系统中默认打开三个文件描述符；第五，在程序的入口点启动执行。

在 UNIX 或 Linux 系统中，进程创建通常使用 `fork()`。一个典型示例如下：

```c
int main() {
    pid_t pid;
    pid = fork();
    if (pid < 0) {
        fprintf(stderr, "Fork Failed");
        exit(-1);
    } else if (pid == 0) {
        execlp("/bin/ls", "ls", NULL);
    } else {
        wait(NULL);
        printf("Child Complete");
        exit(0);
    }
}
```

`fork()` 调用成功后，父进程和子进程拥有几乎相同的地址空间。为了区分父子进程，`fork()` 的返回值提供了判断依据。如果返回值小于零，说明创建进程失败；如果返回值等于零，当前执行的是子进程；如果返回值大于零，当前执行的是父进程，并且返回值就是子进程的 PID。子进程通常会调用 `exec` 系列函数来执行新的程序，而父进程则调用 `wait()` 进入阻塞状态，等待子进程退出的事件发生。子进程退出后，父进程被解除阻塞，继续执行后续代码。这种机制使得父进程能够与子进程同步，并在子进程结束后进行处理。

UNIX 系统将 `fork()` 和 `exec()` 分离，这一设计具有重要的实践意义。它允许 shell 在 `fork()` 之后、`exec()` 之前插入额外的工作，从而支持输出重定向、管道等机制。例如命令：

```bash
wc p3.c > newfile.txt
```

shell 首先使用 `fork()` 创建一个子进程，然后关闭该子进程的标准输出，打开文件 `newfile.txt`，使文件描述符替代原来的标准输出，最后再使用 `exec()` 执行 `wc p3.c`。这样，`wc` 的输出就不会显示在终端上，而是被重定向到 `newfile.txt` 文件中。

另一个例子是管道机制：

```bash
grep -o foo file | wc -l
```

shell 使用 `pipe()` 系统调用创建管道，将第一个进程的输出连接到内核中的管道输入端，将第二个进程的输入连接到同一管道的输出端。第一个命令产生的输出通过管道传递给第二个命令作为输入，从而实现了两个进程之间的通信和协作。

进程终止发生在进程执行完最后一条语句并要求操作系统删除它时。进程可以调用 `exit()` 系统调用来主动终止。终止时，进程可以通过 `wait()` 系统调用向等待它的父进程返回一个状态值。操作系统会回收进程的所有资源，包括物理内存、虚拟内存、打开的文件以及 I/O 缓冲区。此外，父进程也可以通过系统调用终止其子进程。

### 执行模式与模式切换

现代 CPU 至少支持两种执行模式：**内核态**和**用户态**。内核态具有高特权级，用户态具有低特权级。某些指令属于特权指令，只能在内核态下执行，例如修改处理器状态寄存器的指令；某些内存区域也只能在内核态下访问。这种划分的根本目的是保护操作系统及其关键数据结构，避免用户程序干扰甚至破坏系统。

系统启动时，CPU 处于内核态，由引导程序和操作系统完成系统初始化。在准备运行用户代码之前，操作系统会把 CPU 的执行态切换为用户态。应用程序运行在用户态下，无法自行进入内核态，因为修改处理器状态寄存器的指令是特权指令，用户态下不能执行。操作系统重新进入内核态的行为受到严格控制，只有在三类事件发生时才会进入内核态：**系统调用**、**陷阱（trap）**和**硬件中断**。

**模式切换（Mode Switch）**指的是 CPU 在内核态与用户态之间的切换。模式切换不会改变当前正在运行的进程或线程，它只是把栈指针从用户栈切换到内核栈，并保存一组最少的用户空间寄存器。由于虚拟地址空间没有发生变化，模式切换的开销显著低于完整的上下文切换。

模式切换的核心流程可以概括为五步。第一步是保护现场，CPU 自动将用户态下的关键寄存器压入内核栈，确保之后能够准确恢复执行。第二步是权限升级，特权级从用户态切换到内核态，从而获得对硬件和内存的最高访问权限。第三步是内核执行，跳转到系统调用、中断处理或异常处理所对应的内核功能代码，执行具体的系统功能。第四步是恢复现场，从内核栈中恢复用户态寄存器的值。第五步是权限回落，特权级从内核态切换回用户态，程序回到断点处继续执行。其中，需要保存的只是那些中断处理程序、系统调用或异常处理程序会修改的寄存器；不会被修改的寄存器则无需保存。

触发模式切换的三类事件具体如下。

第一类是**系统调用（System Call / Software Interrupt）**。用户程序可以通过执行一条机器指令显式地发起系统调用，请求操作系统提供服务，例如文件读写、进程创建等。这条指令可以在用户态下执行，执行时会产生一次软中断，使 CPU 的特权级提升到内核态，然后跳转到操作系统提供的系统调用代码。系统调用处理完成后，CPU 再切回用户态，返回应用程序继续执行。

第二类是**陷阱（Trap）**。陷阱是由当前运行进程内部产生的错误或异常条件引起的同步事件。典型的例子包括除零运算、非法指令、以及缺页异常。缺页异常是指进程访问的虚拟地址所在页面当前不在物理内存中，操作系统需要将其从磁盘调入内存。由于这些异常是由当前进程执行的指令产生的，因此陷阱属于同步中断。发生陷阱后，CPU 会进入相应的异常处理程序，完成处理后返回用户程序。

第三类是**硬件中断（Hardware Interrupt）**。硬件中断是由当前运行进程之外的设备产生的异步事件，例如键盘输入、定时器中断、网卡数据到达等。它与当前运行进程无关，但会打断当前进程的执行，使 CPU 进入内核态执行中断处理程序。处理完成后，恢复被打断进程的执行。

### 上下文切换与进程切换

**上下文切换（Context Switch）**是指保存当前进程或线程的状态，然后恢复另一个进程或线程的状态并启动其执行。它是多道程序操作系统或多任务操作系统的核心特征，使多个进程或线程能够共享同一个 CPU。

**进程切换（Process Switching）**则是指一个正在运行的进程被打断，操作系统将另一个进程置为运行态，并把控制权转交给它。进程切换可以从三个问题来理解。

第一个问题是：什么事件会触发进程切换？前面提到的三类事件——系统调用、陷阱和硬件中断——一定会触发模式切换，但不一定会触发进程切换。换句话说，进程切换必须以模式切换为前提，但模式切换未必导致进程切换。例如，定时器中断发生时，如果当前进程的时间片已经用完，操作系统可能会进行进程调度，从而触发进程切换。但如果是一次磁盘 I/O 完成中断，则不一定触发进程切换。磁盘读取完成后，操作系统会唤醒等待该 I/O 的阻塞进程，将其放入就绪队列。如果该进程优先级高于当前进程，则可能发生抢占和进程切换；如果优先级较低，则只是进入就绪队列，不会立即切换。

第二个问题是：模式切换与进程切换有什么区别？模式切换只改变 CPU 的执行态，不改变当前运行的进程或线程，因此开销较低。进程切换则要更换当前运行的进程或线程，必然涉及地址空间的变化。一个进程切换发生前一定先发生模式切换，因为操作系统代码需要先获得控制权，才能完成进程调度和上下文切换。

第三个问题是：为了实现一次进程切换，操作系统需要做哪些工作？核心步骤如下：

1. 保存当前进程的处理器上下文，包括程序计数器和所有其他寄存器。
2. 更新当前运行进程的 PCB，例如将其状态从运行态改为就绪态或阻塞态。
3. 将该 PCB 移动到合适的队列中，例如就绪队列、阻塞队列或就绪/挂起队列。
4. 选择另一个进程执行。
5. 更新被选中进程的 PCB，将其状态改为运行态。
6. 更新内存管理数据结构，具体内容取决于地址转换的管理方式。例如在分页系统中，需要将页表基址切换为新进程的页表。
7. 恢复被选中进程的上下文，使其从上次保存的位置继续执行。

进程切换的最大开销并不在于上述寄存器保存和恢复等操作，而在于高速缓存和 TLB 等硬件加速结构的失效。进程切换会导致地址空间改变。当前进程运行期间，cache 中保存的是该进程地址空间中的内容；切换到新进程后，这些内容不再有用，因此新进程刚开始运行时 cache 命中率很低，需要一段时间才能重新建立局部性。类似地，TLB 中缓存的是当前进程的页表项，进程切换后必须刷新 TLB，否则地址转换会出错。由于这些原因，进程切换的开销显著高于线程切换和模式切换。

### 线程与进程的关系

在经典进程模型中，每个进程只有一个控制线程。进程同时具有两个方面的特性：一方面，它是**资源拥有者**，被分配了一个虚拟地址空间，用来保存进程映像，还拥有打开的文件等资源；另一方面，它也是**调度和执行实体**，沿着一条执行路径与其他进程交替运行。

现代操作系统引入线程之后，将这两个特性分离开来。**资源拥有者**仍然称为进程，而**调度和分派单元**称为线程，也常被称为轻量级进程。一个进程内可以有多个线程，这些线程共享进程的代码段、数据段、打开文件等资源，但每个线程拥有自己的寄存器组、程序计数器和栈。多线程进程的地址空间中，除了全局的数据段、代码段和堆之外，每个线程都有自己独立的栈区域，因为每个线程的函数调用历史不同，需要单独的栈来保存各自的局部变量、返回地址和栈帧。

线程的基本组成包括：线程 ID，用于在进程内唯一标识一个线程；程序计数器，指向该线程下一条要执行的指令；寄存器组，保存该线程的 CPU 状态；以及栈，保存该线程的函数调用历史。同一进程内的所有线程共享代码段、数据段和其他操作系统资源，例如打开的文件和信号等。

在进程级别和线程级别上，分别维护着不同的信息。进程级别上包括地址空间、全局变量、打开的文件、子进程、待处理的告警、信号及信号处理程序、记账信息等。线程级别上则包括线程上下文，即寄存器组和程序计数器、栈，以及线程自身的执行状态。

线程切换是指在同一个进程内从一个线程切换到另一个线程。由于这些线程共享同一个虚拟地址空间，线程切换不需要更新页表等内存管理结构，TLB 也不需要刷新，cache 中的内容仍然有效，因此线程切换的额外开销远低于进程切换，速度更快。进程切换则是从属于一个进程的线程切换到属于另一个进程的线程，必须更新内存管理结构，以实现进程之间的地址空间隔离。进程切换虽然开销更高，但它提供了进程级的内存保护和隔离。

### 多线程编程的动机与优点

为了说明多线程的动机，可以看一个场景：一个程序需要向两个不同主机发起远程过程调用（RPC），分别获取数据，再根据两个主机返回的结果进行组合，产生最终输出。

如果使用单线程实现，程序只能依次向第一台主机发出 RPC 请求，等待响应返回，再向第二台主机发出 RPC 请求，再等待响应。程序在等待期间处于阻塞状态，无法执行有用的计算。两个 I/O 操作串行完成，总时间较长。

如果使用多线程实现，可以为每一个 RPC 分配一个独立线程。线程 A 向第一台主机发出 RPC 请求后被阻塞，此时线程 B 被调度执行，向第二台主机发出 RPC 请求。两个远程调用的等待时间可以重叠。第一台主机返回结果后，解除线程 A 的阻塞，线程 A 继续处理；第二台主机返回结果后，线程 B 也完成处理。最后由主线程将两个结果组合成最终输出。多线程版本显著加速了程序的执行。

从总体上看，多线程编程的优点可以归纳为四点。

第一是**响应性**。在交互式应用中，可以用一个线程专门处理用户交互，用其他线程执行冗长的计算或可能阻塞的操作。这样即使某个线程被阻塞，用户交互线程仍然可以继续响应。

第二是**资源共享**。同一进程中的多个线程共享该进程的内存和其他资源。由于共享同一个地址空间，线程之间可以通过全局变量等方式方便地进行通信，而不必经过内核。

第三是**经济性**。相比创建进程和进程上下文切换，创建线程和线程上下文切换的开销更低。同时，同一进程内线程之间通信也无需调用内核，因此更加经济高效。

第四是**可扩展性与多处理器利用**。在多处理器系统或多核系统中，同一个进程的多个线程可以并行运行在不同处理器上，从而充分利用硬件并行性，提高应用程序性能。

与多进程相比，线程还具有以下几个更具体的优势：创建一个线程比创建一个进程更快；终止一个线程比终止一个进程更快；同一进程内两个线程之间的切换成本低于两个进程之间的切换；由于共享相同的地址空间和文件资源，同一进程内线程之间通信无需内核参与。线程也能用于加速应用程序，例如在多 CPU 上并行执行，或者在单 CPU 上使 I/O 与计算重叠。不过，这种加速效果使用多进程也能实现，只是多进程在通信和创建方面开销更高。因此，线程的这些优点中，尤其重要的是快速创建、切换和低开销通信。

需要注意的是，操作系统提供的保护机制是在进程级别实现的。不同的进程可能属于不同的用户，操作系统需要防止一个进程干扰另一个进程。而同一个进程内的多个线程属于同一用户，操作系统在它们之间不提供彼此保护，认为线程间如何协同工作应当由应用程序自身负责。

### 多线程环境的分类

多线程环境可以从两个维度进行分类：系统中可以有多少个地址空间，以及每个地址空间内可以有多少个线程。

根据这两个维度，可以组合出四类典型系统。**单进程单线程**的典型代表是早期的 DOS 系统，整个系统只有一个地址空间，该地址空间内只有一个线程。**单进程多线程**的典型代表是 Java 运行时环境，一个 Java 运行环境中有一个地址空间，但其中可以运行多个线程。**多进程单线程**是传统 UNIX 系统的模型，系统中有多个进程，但每个进程只有一个线程。**多进程多线程**是当代主流系统的模型，例如 Windows 2000、Solaris、Linux 和 Mach，系统中既可以有多个进程，每个进程内又可以有多个线程。

在实际设计应用程序时，如果一个任务可以分解为若干彼此独立、无需频繁通信的工作，那么使用多个进程通常是更好的选择，因为进程之间的隔离性更强。反之，如果多个工作之间需要紧密合作、频繁通信和同步，那么在同一个进程内使用多个线程会更加合适，因为线程间通信开销更低，共享数据更方便。

### 用户级线程（ULT）

用户级线程（User-Level Threads, ULT）的纯实现中，所有线程管理工作都由用户空间的应用程序完成，操作系统内核感知不到线程的存在。内核仍然只看到传统的进程，并不维护线程状态。应用程序通过一个**线程库**来管理用户级线程。线程库是一个运行在用户态的例程包，通常包含创建和销毁线程、在线程之间传递消息和数据、调度线程执行以及保存和恢复线程上下文的代码。

在纯 ULT 模型中，内核空间中保存的仍然是进程表，每个进程对应一个 PCB。而在用户空间中，每个进程内部维护一个私有的线程表，线程表中的每个表项对应一个用户级线程控制块，记录该线程的状态。内核只看到进程，而线程的状态由用户空间的线程库管理。

用户级线程的状态与进程状态之间存在着密切但非等价的关系。可以通过一个具体例子说明。假设进程 B 中有两个用户级线程，线程 1 和线程 2。初始时，进程 B 正在运行，线程 2 的某条指令正在 CPU 上执行。在操作系统看来，CPU 分配给了进程 B，因此进程 B 处于运行态。在线程库看来，线程 2 处于运行态，线程 1 处于就绪态。

第一种情况：线程 2 执行了一个阻塞式系统调用，例如读取磁盘或等待用户键盘输入。该调用经过模式切换进入内核后，操作系统只看到进程 B，于是将进程 B 从运行态变为阻塞态。线程 2 也从运行态变为阻塞态。此时即使线程 1 处于就绪态，也无法获得 CPU 执行，因为整个进程 B 已经被内核阻塞。系统调用完成后，进程 B 回到就绪态，线程 2 也回到就绪态。

第二种情况：发生时钟中断，操作系统内核判断进程 B 的时间片已用完，于是将进程 B 从运行态变为就绪态。此时线程 2 仍然从运行态变为就绪态。进程 B 和线程 2 都被挂起，等待下一次调度。

第三种情况：线程 2 需要等待线程 1 完成某个操作后才能继续执行。由于这是同一进程内两个线程之间的同步，线程库可以将线程 2 置为阻塞态，并将线程 1 从就绪态切换为运行态。此时进程 B 仍然保持运行态，因为 CPU 仍然分配给了进程 B，只是执行线程从 2 变成了 1。

从这三种情况可以看出，用户级线程的运行态并不一定表示其指令正在 CPU 上执行。一个用户级线程要真正运行，必须同时满足两个条件：该线程在自身的线程表中处于运行态，并且它所在的进程也处于运行态，即操作系统已经把 CPU 分配给该进程。

用户级线程的主要优点包括：线程切换不需要切换到内核态，因为线程管理的数据结构都在用户地址空间中；线程调度策略可以由应用程序自行设计，更加灵活；ULT 可以运行在不支持线程的操作系统上，因为内核无需感知线程的存在。

但用户级线程也有明显缺点。第一，如果一个用户级线程执行了阻塞式系统调用，内核会阻塞整个进程，导致该进程内所有线程都无法执行，即使其他线程逻辑上仍然可以运行。第二，如果一个线程触发了缺页异常，内核同样会阻塞整个进程，因为缺页处理可能需要从磁盘调入页面，属于阻塞式操作。第三，用户级线程无法利用多处理器并行性，因为操作系统只看到一个进程，一个进程最多只能分配到一个 CPU，同一进程内的多个用户级线程无法在不同处理器上同时并行执行。

为了缓解阻塞式系统调用带来的问题，一种思路是将阻塞式系统调用改造成非阻塞式系统调用。另一种思路是使用 **jacket 或 wrapper 技术**，即在应用程序与系统调用之间增加一层包装例程。一个线程不直接调用操作系统的 I/O 例程，而是调用应用级的 jacket 例程。jacket 例程会检查 I/O 设备是否处于忙状态。如果设备忙，则线程进入就绪态，并把控制权交给另一个线程；如果设备空闲，才真正执行 I/O 操作。这种技术只能在一定程度上缓解问题，并不能完全解决用户级线程的所有限制。

### 内核级线程（KLT）

内核级线程（Kernel-Level Threads, KLT）的纯实现中，所有线程管理工作都由操作系统内核完成。内核为进程和线程维护各自的上下文信息，线程表也位于内核空间。调度以线程为单位进行。当代操作系统，如 Windows 2000、Solaris 等，通常采用的是内核级线程模型。

在纯 KLT 模型中，内核空间中既维护进程表，也维护线程表。进程表项对应每个进程的 PCB，线程表项对应每个线程的线程控制块。假设系统中有两个进程，一个进程有三个线程，另一个进程有四个线程，那么进程表中有两项，线程表中则有七项。内核通过线程表来管理和调度每一个线程。

内核级线程的优点主要体现在三个方面。第一，内核可以把同一个进程中的多个线程同时调度到多个处理器上并行执行，从而充分利用多处理器架构。第二，如果一个进程中的某一个线程被阻塞，内核可以调度该进程中的另一个线程继续执行，不会导致整个进程的所有线程都被阻塞。第三，内核例程本身也可以是多线程的，从而提高操作系统自身的并行性。

内核级线程也存在一些代价。由于线程管理由内核完成，任何线程控制权转移或阻塞调用都需要涉及系统调用和模式切换。与用户级线程库中一次普通函数调用相比，系统调用的代价要高得多。因此，同样情况下，内核级线程的调度和线程切换开销高于用户级线程。但从功能和并发能力来看，内核级线程更强大，也更符合当代系统的需求。

### 用户级线程与内核级线程的映射关系

在实际系统中，用户级线程与内核级线程之间可能存在不同的对应关系。

**多对一映射**是指多个用户级线程映射到同一个内核级线程。这种模型对应纯 ULT 的实现。操作系统只看到这一个内核级线程，用户空间的线程库管理多个用户级线程。当一个用户级线程阻塞时，内核级线程也会阻塞，进而导致所有映射到它的用户级线程都被阻塞。

**一对一映射**是指每一个用户级线程映射到一个内核级线程。这种模型对应纯 KLT 的实现。每个用户级线程都可以被内核独立调度，因此同一进程内的多个线程可以真正并行执行。

**多对多映射**是指多个用户级线程复用较少数量的内核级线程。例如，一个应用程序中有十个用户级线程，但只映射到三个内核级线程。多对多模型更加灵活，能够结合 ULT 和 KLT 各自的优点：频繁通信的用户级线程可以映射到较少的内部线程上以减少内核参与，同时又能利用内核级线程的并行调度能力。不过，多对多映射的管理更加复杂，需要更精巧的调度和同步机制。

### 线程同步问题

由于同一进程内的所有线程共享相同的地址空间和其他资源，任何一个线程对资源的修改都会影响同一进程中其他线程的执行环境。因此，必须对各个线程的活动进行同步，以避免它们相互干扰，保证共享数据的一致性。线程同步的具体机制将在后续两章中详细讨论。
