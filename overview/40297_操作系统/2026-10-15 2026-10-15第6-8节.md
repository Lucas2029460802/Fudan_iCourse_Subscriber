### 信号量与进程互斥同步

### 从软件方法到 Peterson 算法

在进入更高级的同步机制之前，我们首先回顾此前介绍的纯软件方法。为了解决两个进程之间的互斥问题，Dekker 算法曾经历四次不成功的尝试。第一次尝试是**严格交替（strict alternation）**，通过一个 `turn` 变量规定两个进程 $P_0$ 和 $P_1$ 交替进入临界区。这种方法虽然保证了互斥，但存在严重的性能缺陷：如果一个进程暂时不需要进入临界区，另一个进程也将被其"轮到"的限制所阻塞。第二次尝试允许每个进程检查对方的状态，但无法保证互斥——两个进程可能同时检测到对方不在临界区，从而同时进入。第三次尝试中，进程先表达进入意愿再检测对方状态，可能导致双方都等待对方而陷入死锁。第四次尝试为克服死锁而引入"撤回意愿"的机制，却又可能引发活锁。

**Peterson 算法**则提供了一种比 Dekker 算法更简洁、更优雅的解决方案。该算法使用两个共享变量：布尔数组 `flag[2]`，初始化为 `{false, false}`，表示两个进程各自是否有进入临界区的意愿；以及整型变量 `turn`，用于在两个进程同时有意愿时充当仲裁者。当 $P_0$ 想进入临界区时，它先设置 `flag[0] = true`，然后将 `turn` 置为 1，表示谦让对方。接着进入一个 `while(flag[1])` 的循环，在循环内检查 `turn` 的值：如果 `turn == 1`，说明对方也有意愿并且轮到自己谦让，则暂时将 `flag[0]` 置为 `false`，等待 `turn` 变为 0，再重新设置 `flag[0] = true`。若对方没有意愿（`flag[1] == false`），或者 `turn == 0`，则可以直接进入临界区。退出时，$P_0$ 设置 `turn = 1` 并清除自己的 `flag[0]`。

`turn` 变量的仲裁逻辑值得仔细分析。当两个进程同时想进入临界区时，两者都会先把 `turn` 置为对方的值。由于对同一内存单元的赋值操作在硬件层面是串行化的，后执行的那条赋值语句会覆盖先执行的结果。因此，先执行 `turn` 赋值操作的进程（例如 $P_0$ 先将 `turn` 置为 1），会在后执行的进程（$P_1$ 将 `turn` 置为 0）覆盖之后看到 `turn == 0`，从而满足进入条件；而 $P_1$ 则因为看到 `turn == 1` 而被阻塞。这就保证了即使双方同时有意愿，也只有一个进程能进入临界区。

如果 $P_1$ 已经在临界区内，则此时 `flag[1]` 为 `true` 且 `turn` 为 0。$P_0$ 尝试进入时会将 `flag[0]` 置为 `true`、`turn` 置为 1，然后在循环中检测到 `flag[1] == true` 且 `turn == 1`，因此被阻塞。直到 $P_1$ 退出临界区并清除 `flag[1]` 后，$P_0$ 才能通过。这保证了互斥性，也满足了"一个进程退出后另一个可以立即进入"的基本要求。

软件方法虽然理论上可行，但将互斥责任完全交给程序员极易出错，且普遍存在**忙等待（busy waiting）**的问题，浪费 CPU 周期。这促使我们转向硬件层面的支持机制。

### 硬件支持的互斥机制

硬件支持实现互斥有三种主要途径：关中断、Test-and-Set 指令和 Exchange 指令。

**关中断（Disabling Interrupts）** 仅适用于单处理机系统。在单 CPU 环境中，进程之间的"并发"实际上是交替执行，而非真正意义上的并行。一个进程在运行过程中，操作系统只在三种情况下获得控制权：进程主动发起系统调用、硬件中断发生（如定时器到期或磁盘 I/O 完成），以及执行指令引发异常（如除零、非法特权指令、非法内存访问等）。其中硬件中断是异步的，与当前执行的指令无直接关联；而异常则是同步的，与当前指令密切相关。如果在进入临界区之前关闭中断，且在临界区内不发生异常、不主动调用系统服务，那么硬件中断就不会打断当前进程，进程切换也就不会发生，从而保证了互斥。退出临界区时再打开中断即可。

然而，关中断方案存在两个根本性问题。第一，它**不适用于多处理机**：关闭一个 CPU 上的中断只能阻止该 CPU 上的进程切换，其他 CPU 上的进程仍然可以并行运行并同时进入临界区。第二，将关中断的能力交给用户进程是极其不当的。如果用户进程关闭中断后执行一个空的 `while(1)` 循环，操作系统将永远无法获得控制权，整个系统会挂起。因此，关中断只能作为操作系统内核自身经过严格测试后的特权操作，不能作为一般用户级互斥机制。

**Test-and-Set 指令（TSL）** 的核心在于解决了软件方法中"检查和设置不原子"的问题。在 Dekker 算法的第二次尝试中，进程先测试锁变量的状态，再设置锁变量，这两步之间可能发生交替执行，导致两个进程同时看到锁是打开的状态并同时进入。TSL 指令以单一指令周期原子地完成两个操作：将内存中锁变量的值读入寄存器 `RX`，然后向该内存地址写入一个非零值。由于这是对同一内存位置的读和写操作，硬件通过锁住内存总线来禁止其他 CPU 在此期间访问该内存位置，从而保证了操作的不可分割性。

从逻辑层面看，TSL 的行为可以描述为：对锁变量 `bolt` 执行 `test_and_set` 操作，若 `bolt` 原本为 0（锁打开），则将其置为 1（锁上）并返回 `true`；若原本为 1（已锁），则保持为 1 并返回 `false`。进程进入临界区前在 `while` 循环中反复执行 `test_and_set(bolt)`，只有捕获到 0 到 1 的转换（即自己亲手将锁锁上）的进程才能进入临界区。退出时执行 `bolt = 0` 解锁。

**Exchange 指令（XCHG）** 是另一种等价的机器指令方案。它以原子方式交换两个位置的内容——通常是一个寄存器和一个内存字。在信号量的上下文中，进程可以将一个寄存器置为 1，然后与锁变量 `bolt` 进行交换。如果换回的值是 0，说明该进程成功将锁从 0 变为 1，可以进入临界区；如果换回的值是 1，说明锁本已锁上，需要继续循环。在 Intel x86 架构上，`XCHG` 指令就是用于底层同步的典型实现，其汇编代码模式为：向寄存器存入 1，与 `LOCK` 交换，比较寄存器是否为 0，若非零则跳回循环，否则进入临界区。

机器指令方法的**优点**是：适用于任意数量的进程，无论是单处理机还是共享内存的多处理机系统；实现简单且易于验证正确性；每个临界区只需配一个锁变量即可。但其**缺点**同样显著。首先是**忙等待**：等待进入临界区的进程在循环中不断执行 TSL 或 XCHG，消耗处理器时间。其次是可能产生**饥饿（starvation）**：当临界区内的进程退出并释放锁后，多个等待进程竞争抢锁，哪个进程成功是不确定的，某些进程可能长期得不到机会，不满足有限等待的要求。第三是可能产生**死锁**，具体表现为**优先级倒置（priority inversion）**：假设低优先级进程 $P_0$ 持有临界区的锁，高优先级进程 $P_1$ 需要访问同一临界区。在具有优先级调度的系统中，$P_1$ 会抢占 $P_0$ 的 CPU 资源，但 $P_1$ 进入临界区的尝试会被锁阻塞而进入忙等待，而 $P_0$ 因优先级低无法获得 CPU 来释放锁，从而形成死锁。解决优先级倒置问题的经典方法是**优先级继承协议（priority-inheritance protocol）**。

### 信号量的定义与基本操作

信号量（semaphore）是操作系统提供的一种更高级的同步机制，也是整个同步部分的重中之重。一个信号量在概念上是一个具有整型值的变量，但从面向对象的视角看，它是一个只允许执行三种操作的对象：**初始化**将其设置为非负整数值，**wait 操作**将其值递减，**signal 操作**将其值递增。除此之外不能对信号量做任何其他操作。

信号量的内部数据结构包含两个字段：一个整型计数器 `count` 和一个阻塞进程队列 `queue`。`wait` 操作的实现是：先将 `s.count` 减一；若结果小于 0，则将当前进程放入 `s.queue` 中并阻塞。`signal` 操作的实现是：先将 `s.count` 加一；若结果小于等于 0，则从 `s.queue` 中移除一个进程并将其放入就绪队列。注意两个操作中不等号的细微差别：`wait` 中是"小于 0"，`signal` 中是"小于等于 0"。这个细节反映了计数值为负时对应的含义——负数的绝对值代表在信号量上阻塞等待的进程数量。

信号量分为两类。**计数信号量（counting semaphore）** 的 `count` 可以是任意非负整数，含有定量的信息。**二元信号量（binary semaphore）** 的 `value` 只能取 0 或 1，仅能表达定性的状态。二元信号量上的 `waitB` 操作逻辑为：若 `value == 1`，则将其置为 0 并继续执行；若 `value == 0`，则阻塞当前进程。`signalB` 操作逻辑为：若阻塞队列为空，则将 `value` 置为 1；否则解除一个阻塞进程。由于 `value` 只能取 0 或 1，对一个已经为 0 的二元信号量再做 `waitB` 操作只会继续阻塞，而不会有累积效应。需要强调的是，`wait` 和 `signal` 操作本身都是**原子操作**——信号量自身就是一个临界资源，对它的访问必须互斥进行。

### 信号量的语义解读与互斥实现

信号量的 `count` 值具有明确的双重语义。当 $count \geq 0$ 时，它表示还可以执行多少次 `wait` 操作而不被阻塞，也就是可用资源的数量。当 $count < 0$ 时，其绝对值表示在该信号量上阻塞等待的进程数量。例如，若信号量初始化为 3，则前三次 `wait` 操作将依次把 `count` 从 3 降到 0，均不会阻塞；第四次 `wait` 会使 `count` 变为 -1 并阻塞调用进程，-1 恰好对应一个进程在等待。

信号量的典型运行可以通过四个进程 $A, B, C, D$ 的场景来理解。进程 $D$ 不断生产结果，$A, B, C$ 消费这些结果。信号量 `s` 初始化为 1，表示系统中有 1 个可用结果。$A$ 运行时执行 `wait(s)`，将 `s` 从 1 减为 0，消耗掉唯一的结果后回到就绪队列。$B$ 随后运行，也需要消费结果，执行 `wait(s)` 将 `s` 从 0 减为 -1，因结果小于 0 而被阻塞。此后 $D$ 运行并生产了一个新结果，执行 `signal(s)` 将 `s` 从 -1 增为 0，由于增量后等于 0，满足小于等于 0 的条件，便从阻塞队列中解除 $B$ 的阻塞。后续 $C$、$A$、$B$ 依次消费结果时，`s` 会逐步变为 -1、-2、-3，表示有三个进程在等待。

利用信号量实现互斥极为直接。定义一个互斥信号量 `s = 1`，任何进程进入临界区前执行 `wait(s)`，退出时执行 `signal(s)`。第一个进程执行 `wait(s)` 将 `s` 从 1 减为 0，不会被阻塞并进入临界区。后续进程执行 `wait(s)` 时，`s` 会从 0 变为 -1 并被阻塞。当临界区内的进程执行 `signal(s)` 时，`s` 从 -1 增为 0，解除一个阻塞进程使其进入临界区。这个被解除的进程完成后再 `signal(s)`，`s` 继续增加，依次唤醒后续等待者，直到所有等待进程都完成后 `s` 回到 1。需要特别注意，互斥信号量的初始值必须为 1，不能为 2 或其他值。若初始化为 2，则前两个进程都能通过 `wait(s)` 而同时进入临界区，互斥将被破坏。

### 生产者-消费者问题：二元信号量方案

生产者-消费者问题描述了一组并发进程共享一个有限或无限缓冲区的情形。生产者将生产的数据项放入缓冲区，消费者从缓冲区中取出并消费。缓冲区是共享的临界资源，任意时刻只能有一个生产者或消费者访问它，因此存在互斥问题；同时，消费者必须在缓冲区非空时才能取数据，生产者则必须在缓冲区有余量时才能放数据，这是同步约束。

首先考虑**无限缓冲区**的情形，此时生产者不受空间约束，问题相对简化。从数据结构的视角，缓冲区用一个线性数组 $b$ 表示，两个指针 `in` 和 `out` 分别指向下一个空位和下一个可消费的数据项。生产者执行 `b[in] = v; in++;`，消费者在 `in > out` 时执行 `w = b[out]; out++;`。当 `in == out` 时，缓冲区为空。

使用二元信号量的解决方案引入了三个变量：互斥二元信号量 `s = 1`，用于保护缓冲区和共享变量 `n`（缓冲区中数据项的数量）；同步二元信号量 `delay = 0`，用于表达"缓冲区从空变为非空"的状态变化；以及整型变量 `n = 0` 记录定量的产品数量。生产者生产出数据项后，执行 `waitB(s)` 进入临界区，将数据放入缓冲区并执行 `n++`。关键步骤是：如果 `n == 1`（即 `n` 从 0 变为 1，缓冲区经历了从无到有的质变），则执行 `signalB(delay)`。然后执行 `signalB(s)` 退出临界区。

消费者的逻辑对应而复杂。消费者首先执行 `waitB(delay)`。由于 `delay` 初始值为 0，第一个运行的消费者必然阻塞在此处。只有当生产者放入第一个产品并执行 `signalB(delay)` 后，`delay` 才变为 1，消费者才能通过。通过后执行 `waitB(s)` 进入临界区，取出一个数据项并执行 `n--`。退出临界区后，消费者检查如果 `n == 0`（即刚刚取出了最后一个产品，缓冲区从有变为无），则执行 `waitB(delay)` 将自己再次阻塞在 `delay` 上，以维护"缓冲区为空"的状态。

这一方案的核心困难在于二元信号量只具备**定性的表达能力**，即只能表示"有"或"无"的状态，而产品数量 $n$ 的定量信息必须靠普通整型变量维护。`if` 条件的编写必须精确捕捉质变时刻：`n == 1` 对应从无到有，`n == 0` 对应从有到无。这种通过 `if` 语句捕捉状态质变的思维方式，在后续读者-写者问题和管程实现中会反复用到。

然而，这个二元信号量方案存在一个精细的缺陷。消费者在临界区内执行 `n--` 后退出临界区（`signalB(s)`之后），才检查 `n == 0`。但这时的 `n` 可能已经被随后进入临界区的生产者修改过了。具体来说，消费者取走了最后一个产品使 `n` 变为 0，但生产者随后放入新产品又使 `n` 变为 1。当消费者执行 `if (n == 0)` 判断时，看到的 `n` 是 1，因此不会执行 `waitB(delay)`，导致 `delay` 的状态与实际缓冲区状态不一致。后续消费者可能误以为缓冲区中有产品而执行取数据操作，引发错误。解决方法是引入一个**局部变量**，在临界区内记录 `n--` 之后的值，退出临界区后用局部变量进行判断，避免共享变量被并发修改的影响。

### 生产者-消费者问题：计数信号量方案

使用计数信号量解决生产者-消费者问题显著更简洁。对于无限缓冲区，生产者仅需一个互斥信号量 `s = 1` 来保护缓冲区的访问。生产者的代码为：`produce(); wait(s); append(); signal(s);`，没有同步约束的必要。消费者的同步约束通过计数信号量 `n = 0` 表达，`n` 表示缓冲区中数据项的数量。消费者取产品前执行 `wait(n)`，若 `n > 0` 则通过，随后执行 `wait(s); take(); signal(s); consume();`。生产者放入产品后执行 `signal(n)` 将 `n` 递增，通知消费者有新的产品可用。

这里涉及两个连续 `wait` 操作的次序问题。消费者必须先执行 `wait(n)` 再执行 `wait(s)`，顺序不能颠倒。若先执行 `wait(s)` 获得缓冲区访问权，然后执行 `wait(n)` 时发现缓冲区为空而被阻塞在 `n` 上，此时消费者持有互斥信号量 `s` 却无法释放。生产者虽然可以生产产品，但执行 `wait(s)` 时会被阻塞，无法将产品放入缓冲区。这就形成了死锁：消费者等产品，生产者等缓冲区访问权。一般原则是：**互斥信号量的 `wait` 应当放在最内层**，因为它"用完即放"，持有时间短；同步信号量的 `wait` 放在外层，因为它可能长时间阻塞，不应在阻塞期间持有互斥锁。

对于**有限循环缓冲区**，需要考虑容量限制，因此额外引入第三个信号量 `e = sizeofbuffer`，表示缓冲区中空单元的数量。生产者执行 `produce(); wait(e); wait(s); append(); signal(s); signal(n);`，消费者执行 `wait(n); wait(s); take(); signal(s); signal(e); consume();`。生产者在放入产品前消耗一个空单元（`wait(e)`），同时在放入产品后增加一个产品计数值（`signal(n)`）；消费者取出产品前消耗一个产品（`wait(n)`），取出后释放一个空单元（`signal(e)`）。这里生产者中 `wait(e)` 和 `wait(s)` 的次序、消费者中 `wait(n)` 和 `wait(s)` 的次序同样不可颠倒，否则生产者可能在等待空单元时持有互斥锁，而消费者无法取出产品来释放空单元，形成死锁。

### 信号量的实现与忙等待的转化

信号量操作本身必须是原子的，这要求 `wait` 和 `signal` 的实现需要底层同步机制的支持。在**单处理机**上，可以通过关中断来实现。`wait(s)` 先禁止中断，执行 `s.count--`，若结果小于 0 则将进程放入阻塞队列并阻塞，然后允许中断。`signal(s)` 类似地先禁中断，执行 `s.count++`，若结果小于等于 0 则移出一个阻塞进程到就绪队列，然后开中断。由于单处理机上操作时间很短，这种方法是合理的。

在**多处理机**上，可以使用 Test-and-Set 指令来保护信号量内部结构。信号量结构增加一个整型字段 `s.flag`，作为保护信号量自身的锁变量。`wait(s)` 的实现为：先执行 `while(testset(s.flag))` 忙等待获取 `s.flag`，然后执行 `s.count--` 及对应的阻塞逻辑，最后将 `s.flag` 置为 0 释放。`signal(s)` 的结构类似。

这里有一个值得深入探讨的问题：既然 Test-and-Set 有忙等待的缺点，为什么还要用它来实现信号量？关键在于**临界区时间粒度**的转化。假设打印机是临界资源，打印操作耗时很长。若直接用 Test-and-Set 保护打印机，等待进程将在循环中忙等待很长时间，严重浪费 CPU。而信号量将 `wait` 和 `signal` 的操作限制在十几条机器指令之内，非常快速。用 Test-and-Set 保护的是信号量这个**小的临界资源**，忙等待的持续时间极短。一旦进程获取了信号量后发现打印机被占用（需要等待），它会被阻塞在 `s.queue` 上并让出 CPU，不再忙等待。这样，对打印机的长时间等待被转化为对信号量的短时间忙等待，大幅降低了忙等待的发生概率和 CPU 浪费，提升了整体系统性能。

### 理发店问题

理发店问题是一个技术上简单但结构上较为复杂的经典同步问题。场景配置为：三张理发椅、三名理发师、一张可坐四人的沙发、一个站立等候区，以及一个收银台。理发店最多容纳 20 名顾客。三名理发师同时可以为三个顾客理发，此外还需要有人承担收银员的角色，但由于总共只有三人，任意时刻最多有三人同时工作（无论是理发还是收款），这一约束由一个计数信号量 `coord = 3` 来管理。

顾客的行为流程为：首先 `wait(max_capacity)`，其中 `max_capacity` 初始化为 20，表示店内容量约束。若店内已有 20 人，新顾客被阻塞在此。进店后 `wait(sofa)`，`sofa` 初始化为 4，表示沙发上可坐四位。坐上沙发后，`wait(barber_chair)`，`barber_chair` 初始化为 3，表示三张理发椅。获得到理发椅后从沙发起身，执行 `signal(sofa)` 释放一个沙发位置。坐上理发椅后发送 `signal(cust_ready)`通知理发师顾客已就绪，然后 `wait(finished)` 等待理发完成。理发完成后离开理发椅，去收银台付款（`signal(payment)`），等待收据（`wait(receipt)`），最后离开理发店（`signal(max_capacity)` 释放一个容量）。

理发师的行为为：`wait(cust_ready)` 等待顾客入座，`wait(coord)` 获取一个"工作人员名额"，执行 `cut_hair()` 理发，然后 `signal(finished)` 通知顾客理完。随后 `wait(leave_b_chair)` 等待顾客离开理发椅，再 `signal(barber_chair)` 释放理发椅。收银员的行为为：`wait(payment)` 等待顾客付款，`wait(coord)` 获取名额，执行 `accept_pay()` 收款并 `signal(receipt)` 给顾客收据，最后 `signal(coord)` 释放名额。

这个基础版本存在一个隐蔽的问题：由于有三张理发椅，三个顾客可能同时在等待 `finished` 信号。理发师发出 `signal(finished)` 时，会按照 `finished` 阻塞队列中的 FIFO 顺序唤醒顾客，即"先坐上理发椅的先被唤醒"。然而，不同顾客所需的理发时间不同，第三个坐上理发椅的顾客可能最先理完，但他的 `finished` 信号却会唤醒阻塞队列中排在最前面的、可能尚未理完的顾客。这是因为理发师不知道自己服务的具体是哪个顾客，信号无法定向传递。

改进方案引入了**顾客编号**机制。新增全局变量 `count` 和一个互斥信号量 `mutex1` 来保护它。每位顾客进店时在 `mutex1` 保护下执行 `count++` 并获取一个唯一的 `custnr`。当顾客坐上理发椅时，在 `mutex2` 保护下将自己的编号入队，然后发送 `signal(cust_ready)`。理发师被唤醒后，在 `mutex2` 保护下从队列中取出一个顾客编号 `b_cust`，理发完成后执行 `signal(finished[b_cust])`，其中 `finished` 是信号量数组，每个顾客有自己独立的信号量。这样，理发师就能精确唤醒对应的顾客，避免了错位唤醒的问题。

### 读者-写者问题概述

读者-写者问题是下一个要重点解决的问题，其结构与生产者-消费者问题有本质区别。生产者-消费者问题中，生产者和消费者都同时担任读者和写者的角色——生产者要读 `in` 指针、写缓冲区数据；消费者要读 `out` 指针、取走数据。而读者-写者问题中，进程的角色是严格区分的：读者进程只读取数据区而不修改；写者进程只对数据区进行写操作。

问题的约束条件为：任意数量的读者可以同时读取数据区，因为多人读取同一份数据互不影响；写者必须独占访问，任意时刻最多只能有一个写者在写；读者和写者之间互斥，即写者在写时读者不能读，读者在读时写者不能写。如果简单地将所有读者和写者都用互斥信号量串行化，虽然能保证正确性，但会极大地降低并发度——即使全是读者，也只能一个一个地读，这显然是不合理的。问题的核心挑战在于：既要允许读者之间的并发，又要保证读者与写者之间的互斥，同时还要处理读者持续到达可能导致的写者饥饿问题。下一节课将详细介绍这一问题的具体解决方案。
