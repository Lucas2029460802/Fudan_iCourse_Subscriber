### Docker Compose 的定位与基本命令

本节课的核心主题是多容器管理问题，即当系统从单个容器扩展到多个容器时，如何定义、启动、停止和维护这些容器的整体生命周期。Docker Compose 正是解决这一问题的声明式编排工具。

从技术背景看，微服务架构要求将单体系统拆分为多个独立服务，每个服务在独立容器中运行。仅掌握单容器的构建、启动、网络和存储配置远远不够；当多个容器需要协同工作时，就需要编排层面的工具来统一管理。Docker Compose 的约束在于：它管理的多个容器必须运行在 **同一台服务器** 上。如果容器分布在不同服务节点、IP 地址不同，Compose 就无法胜任，此时需要升级到 Docker Swarm 或 Kubernetes。

Compose 的核心命令中，`docker compose up` 负责构建（可选）、创建、启动并连接到 Compose 文件中定义的服务容器。首次运行时，Compose 会根据 `compose.yaml` 创建并启动服务容器；当服务配置或镜像发生变化时，Compose 会停止并重新创建受影响容器，同时保留已挂载的 Volume。使用 `-d` 参数可以在后台运行，前台模式下按 `Ctrl+C` 会停止容器，后台模式退出命令行后容器继续运行。`--force-recreate` 参数可以强制重建容器。

`docker compose down` 用于停止并删除项目中的服务容器和 Compose 创建的网络。需要注意的是，默认情况下 **Volume 不会被删除**，镜像也不会被删除；只有指定 `-v/--volumes` 时才会删除命名卷和匿名卷，指定 `--rmi` 时才会删除相关镜像，而 external 卷永远不会被删除。`docker compose stop` 则是临时停止服务容器但不删除容器，保留容器可写层、网络定义和 Volume，之后可以使用 `docker compose start` 恢复同一批已有容器。如需在非项目目录下操作，可通过 `-f` 指定 Compose 文件路径，或使用 `-p` 指定项目名称。

### Compose 的核心资源与应用模型

Compose 的配置围绕三个核心资源展开：**服务（Services）**、**存储卷（Volumes）** 和 **网络连接（Networking）**。

容器与虚拟机的本质区别在于：容器共享宿主机的操作系统内核，不会把 OS kernel 打包进镜像，因此体积远小于虚拟机。容器内产生的数据实际存储在宿主机操作系统的某个文件夹下，这就引出了 Volume 映射的概念。通过把容器内部文件夹映射到宿主机文件夹，即使容器被删除，挂载数据仍然保留，重启容器后此前的数据依然有效。这一机制对数据库容器尤其关键：数据库更新或重建后，生产数据和测试数据都能继续保留。

Compose 文件采用 YAML 格式，以缩进表示层级关系。根节点 `services` 是唯一必需的 key，其下每个缩进项代表一个服务。最基本的 Compose 文件结构通常包括：`services` 下定义 `web` 和 `redis` 两个服务；`web` 服务通过 `build: .` 指定构建目录和 Dockerfile，通过 `command` 指定启动命令，通过 `ports` 定义端口映射（如 `"5000:5000"`），通过 `volumes` 定义存储挂载（如 `.:/code`），通过 `environment` 传入环境变量（如 `PYTHONUNBUFFERED=1`）；`redis` 服务则直接使用 `image: redis:latest` 指定官方镜像，无需构建。服务要么使用 `build` 从源码构建镜像，要么使用 `image` 直接引用仓库中已有镜像。

旧版 Compose 文件通常以 `version: '3'` 开头声明版本，但当前新版 Compose 已不要求必须写 `version`，可以直接从 `services` 开始。可选的顶层 `name` 字段用于指定项目名称，该名称会显示在 Docker Desktop 的镜像列表中作为折叠项。

仅指定镜像名而不加标签版本时，Compose 默认使用 `latest` 标签。在实际使用中建议显式指定版本号，以确保可复现性——如果仓库持续推送新版本，上一次正常运行的配置可能因镜像更新而出现不可预期变化。

### 服务依赖与 restart 策略

在多容器应用中，服务间的启动顺序是一个必须妥善处理的问题。Compose 提供 `depends_on` 字段来声明依赖关系：若某服务的 `depends_on` 中声明了另一个服务，Compose 会在启动该服务前先启动其依赖服务。如果一个服务不依赖任何容器，它会被第一个启动；后续服务按依赖拓扑依次启动。

但依赖启动顺序并不等于功能就绪。`depends_on` 仅保证容器“起来了”，无法保证容器内部的应用程序已真正完成初始化。典型场景是数据库容器：DB 容器启动后，数据库进程本身还需要一段初始化时间；如果此时依赖它的 API 容器立即启动并尝试读取数据库，很可能因为数据库尚未就绪而失败。为此，Compose 支持在 `depends_on` 中配合 `condition: service_healthy`，要求被依赖服务通过健康检查后才继续启动后续服务。

`restart` 策略常用的取值包括：`no` 表示启动失败后不再重启；`on-failure` 仅在进程以非零退出码退出时重启，即由于异常、错误导致退出时重启；`always` 表示容器停止后总是尝试重启；`unless-stopped` 与 `always` 类似，但手工停止后不再自动重启。具体选择应根据服务特性和运维要求确定。

### 环境变量与配置外部化

将数据库密码、用户名等敏感信息直接写在 Compose 或 Docker 指令中是不安全且不便复用的做法。更规范的方式是使用 **`.env` 文件** 进行变量插值。`.env` 文件以键值对形式存放环境变量，例如 `TAG=V1.5`；在 Compose 文件中使用 `${TAG}` 占位符引用，执行时实际值会替换占位符。这种方式尤其适合本地密钥管理：不应将这些敏感文件提交到 GitHub 等共享代码库中。不同环境可以各自维护独立的 `.env` 文件，按需配置不同的数据库用户名、密码和镜像版本。

将镜像版本号也写入 `.env` 文件是一种常见实践。这样当需要从开发标签切换为正式版本标签，或更新多组服务镜像版本时，只需在 `.env` 中修改对应变量即可，无需逐条修改 Compose 文件。数据库连接字符串同样可以通过 `${MYSQL_PASSWORD}`、`${MYSQL_DB}` 等环境变量动态生成，使配置文件与运行环境解耦。

### Compose 网络

在最简单的情况下，执行 `docker compose up` 时，Compose 会为项目创建默认网络，名称通常为 `<project>_default`。所有未显式声明网络的服务都会自动加入该默认网络，并可通过服务名直接互访，无需关心具体 IP 地址。例如，若 `db` 服务未指定网络，它以服务名 `db` 加入默认网络，`web` 服务就可以直接通过 `db` 这个服务名访问数据库。

在更复杂的设计中，可以为不同服务分配不同网络，实现服务间的网络隔离。如果两个服务之间不存在业务关联，将它们放入不同网络后，二者无法直接通信。当某个服务需要同时被多个网络中的服务访问时，可以让该服务加入多个网络。Networks 是 Compose 文件中与 `services`、`volumes` 并列的顶层配置项，通常在文件末尾声明网络名称及其 driver（默认使用 `bridge` 桥接驱动）。

### Compose 更新应用

在持续开发迭代的场景下，应用代码或镜像版本会频繁变化。Compose 提供了极为简洁的更新机制：当镜像版本变更或 build 目录中的源码变化后，只需更新 Compose 文件中的镜像版本或 build 内容，然后重新执行 `docker compose up -d`。Compose 会自动检测配置或镜像发生变化的服务，停止并重建受影响容器，无需手工逐条删除旧容器再执行 `docker run`。其他未变化的服务保持运行，已挂载的 Volume 也继续保留。

### 三容器示例：图书 API 系统

课堂演示的示例系统包含三个服务：数据库使用 PostgreSQL，后端 API 是自研 Node.js 应用，数据库管理器使用官方 Adminer 镜像。架构为：用户通过宿主机 5555 端口访问 API 的 80 端口；用户通过宿主机 8080 端口访问 Adminer 的 8080 端口；API 和 Adminer 都需要与 PostgreSQL 数据库通信。该示例没有开发独立前端，测试时通过 Postman 发送 HTTP 请求来验证容器间功能。

#### 项目结构与服务定义

项目目录包含 `backend`、`database` 文件夹和 `compose.yml`。`backend` 是自研服务的源码目录，内含 Dockerfile；`database` 文件夹包含数据库初始化脚本 `init-db.sql`。Compose 文件中顶层的 `name: compose-lab` 声明项目名称。`services` 下定义了三个服务：`backend`（对应图中的 API）、`db-admin`（对应 Adminer）和 `lab4-db`（对应 PostgreSQL 数据库）。

`backend` 服务使用 `build: ./backend`，表示从该目录下的 Dockerfile 构建镜像；`container_name: lab4-api` 为容器指定固定名称。它定义的环境变量包括 `PGUSER=admin`、`PGPASSWORD=admin`、`PGDATABASE=books`、`PGHOST=lab4-db`、`PGPORT=5432`，用于后端连接数据库。端口映射为 `"5555:80"`，网络加入 `lab4-db-network`。该服务的 Dockerfile 采用典型 Node.js 应用构建流程：以 `node:14-alpine` 为基础镜像，设置工作目录 `/usr/src/app`，先拷贝 `package*.json` 并执行 `npm ci` 安装依赖，再拷贝其余源码，暴露 80 端口，最后通过 `CMD ["npm","run","start"]` 启动服务。先拷贝依赖清单再安装、最后拷贝源码的分层策略，可以有效利用 Docker 镜像构建缓存。

`db-admin` 服务使用 `image: adminer:4`，显式指定版本号保证确定性；`container_name: lab4-adminer`；端口映射 `"8080:8080"`；网络加入 `lab4-adminer-network`。它有 `depends_on`，依赖 `lab4-db` 且 `condition: service_healthy`，这是与课堂上前面 PPT 所讲内容的差异之处——不仅要定义依赖，还要通过健康检查确保数据库真正就绪后，Adminer 才被启动。

`lab4-db` 服务使用 `image: postgres:16-alpine`，`container_name: lab4-db`。它同时加入 `lab4-db-network` 和 `lab4-adminer-network` 两个网络，使得 API 和 Adminer 都能通过各自网络访问数据库，但 API 与 Adminer 因处于不同网络而无法相互通信。这种网络划分体现了设计上的约束：两个互不相关的服务不应具有相互通信的能力。

#### 数据库初始化与持久化

`lab4-db` 定义了两类 Volume 映射。第一类是将宿主机上的 `./database/init-db.sql` 映射到容器内的 `/docker-entrypoint-initdb.d/init-db.sql`。PostgreSQL 容器首次启动时会自动执行该目录下的初始化脚本，创建 `books` 表。`init-db.sql` 的内容为：`CREATE TABLE IF NOT EXISTS books (id serial PRIMARY KEY, title varchar NOT NULL, author varchar NOT NULL)`。第二类映射是 `lab4-db-volume:/var/lib/postgresql/data`，将 PostgreSQL 数据目录挂载到命名卷 `lab4-db-volume`，实现数据的持久化存储。这个命名卷不需要指定宿主机具体路径，由 Docker 自动管理。

数据库环境变量定义了 `POSTGRES_USER=admin`、`POSTGRES_PASSWORD=admin`、`POSTGRES_DB=books`。课堂也指出，将这些用户名和密码直接写在 Compose 文件里属于“开倒车”的写法，正确做法是使用 `.env` 文件管理。

#### 健康检查

`healthcheck` 是整个示例设计中非常关键的一环。测试命令为 `test: ["CMD-SHELL", "pg_isready -U admin -d books"]`，`interval: 5s` 表示每 5 秒检查一次，`timeout: 3s` 表示单次检查超时时间为 3 秒，`retries: 5` 表示连续失败 5 次才判定为不健康。当 `pg_isready` 确认 PostgreSQL 已就绪后，`lab4-db` 才被认为 `healthy`，此时 `depends_on` 中带有 `condition: service_healthy` 的 `db-admin` 才会启动。

#### 顶层卷和网络声明

Compose 文件底部声明了 `volumes: lab4-db-volume:` 和 `networks: lab4-db-network: driver: bridge` 以及 `lab4-adminer-network: driver: bridge`。这与 Compose 核心资源的三个层级相吻合：`services` 定义服务，`volumes` 声明存储卷，`networks` 声明网络。

#### 执行过程与验证

执行 `docker compose up -d` 后，终端输出展示了完整的启动过程：首先从 Dockerfile 构建 `compose-lab-backend` 镜像；创建 `compose-lab_lab4-adminer-network` 网络、`compose-lab_lab4-db-volume` 卷和 `compose-lab_lab4-db-network` 网络；启动 `lab4-api` 容器；`lab4-db` 进入 Waiting 状态等待健康检查通过；当 `lab4-db` 变为 Healthy 后，`lab4-adminer` 随即启动。重复执行 `docker compose up -d` 且配置未变时，输出仅为 `Running` 或 `Healthy`，不会重建。

验证流程通过 Postman 完成。发送 `GET localhost:5555/api/books/` 请求，初始返回 200 OK 和空数据。随后使用 POST 请求向同一接口发送 JSON 格式的书本数据，body 中包含 `title` 和 `author` 字段（如 Harry Potter 和 Rowling），返回 201 并附带新书的 ID。在 Adminer 中通过 `http://localhost:8080` 登录，系统选择 PostgreSQL，服务器填 `lab4-db`，用户名和密码均为 `admin`，数据库为 `books`。登录后可查看 `books` 表结构和数据，也可以直接在 Adminer 中插入新记录。再次通过 Postman 查询时，返回的数据与数据库内容一致。

#### down 与数据持久化验证

执行 `docker compose down` 会移除三个容器和两个网络，但命名卷 `compose-lab_lab4-db-volume` 不会被删除。重新执行 `docker compose up -d` 后，通过 Postman 查询仍然返回此前存入的两条数据，证明数据确实持久化。若执行 `docker compose down -v`，输出中会额外多出 `Volume compose-lab_lab4-db-volume Removed`，此时命名卷被删除。再次启动时数据库重新初始化，变为空库，Postman 查询返回空数据。

若在非项目目录下直接执行 `docker compose down`，Compose 因找不到 `compose.yml` 会报错；此时可以通过 `-f` 指定文件路径，或使用 `docker compose -p compose-lab down` 通过项目名称定位到待关闭的项目。

### Docker Swarm Mode 概述

Docker Swarm 是 Docker Engine 内置的集群管理模式，能够将多个 Docker 节点组成集群，并以服务为单位进行调度、扩缩容和故障恢复。与 Compose 仅管理单机多容器不同，Swarm 面对的是分布式节点集群。Swarm Mode 适合学习集群编排核心概念和部分中小规模场景，但其生态和扩展能力通常小于 Kubernetes。

从架构上看，Swarm 节点具有 manager 或 worker 角色。多个 manager 通过 Raft 算法维护一致的集群控制状态，形成 Raft consensus group，并共同访问 Internal Distributed State Store。Manager 节点负责管理集群，其中具有 leader 身份的 manager 负责将任务分配到 worker 节点。Manager 默认也可以运行服务任务，但可以通过将 `availability` 设置为 `drain` 来仅承担管理职责。Worker 接收 manager 分配的任务并运行容器，但不参与 Raft 管理状态。高可用性依赖于多数 manager 节点保持在线。

### Raft 共识算法

Raft 是一种复制状态机共识算法，通过领导者选举、日志复制和多数派提交，使多个管理节点对已提交状态达成一致。Raft 节点具有 Leader、Follower 和 Candidate 三种角色。正常情况下只有一个 Leader，负责接收状态变更、复制日志并推动提交。当 Leader 失效时，系统通过选举产生新 Leader，从而保证高可用。

Raft 的特点鲜明：一是易于理解，通过明确的角色、任期、选举和日志复制规则提高可理解性；二是可用性，只要多数投票节点可通信并正常工作，集群就能继续提交新的状态变更；三是安全性，Raft 保证已提交日志的顺序和状态机应用的一致性；四是适用性广，常用于分布式存储、配置管理和集群控制状态管理。

#### 选举过程

选举过程的触发条件是：Follower 在随机选举超时时间内未收到有效 Leader 消息。Leader 正常工作时会持续向 Follower 同步消息；一旦 Leader 失效，Follower 超时后增加任期、转为 Candidate 并发起选举。投票过程中，每个节点在同一任期内最多投一票。Candidate 只有在其日志至少与投票者一样新时，才可能获得投票。若 Candidate 获得多数投票即成为 Leader；如果无人获得多数，则进入新任期重新选举。

#### 日志复制过程

Leader 接收新的集群状态变更时，将其追加为本地日志条目。随后 Leader 将日志条目发送给 Follower，Follower 持久化后返回确认。日志复制到多数投票节点并满足 Raft 提交规则后，Leader 推进提交索引，各节点按相同顺序把已提交条目应用到状态机。

#### 容错能力

Swarm 的 manager 数量决定控制平面的法定人数和 manager 故障容忍能力。若有 $n$ 个 manager，在保持法定人数的前提下最多可容忍 $\lfloor(n-1)/2\rfloor$ 个 manager 失效。例如 3 个 manager 最多容忍 1 个失效；4 个 manager 同样只能容忍 1 个失效。因此通常使用奇数个 manager，并根据故障域进行部署。增加 worker 不会提高 manager 法定人数的容错能力，因为容错只针对任务调度层面的 manager 角色。

### Swarm 服务模型

Swarm 采用声明式服务模型。用户声明服务镜像、副本数、网络和更新策略等期望状态，由 manager 持续协调。服务定义包括镜像、命令、端口、网络、资源、更新策略和副本模式等，manager 据此创建任务，每个任务通常运行一个容器。扩展服务就是改变期望任务副本数，Swarm 负责创建、停止或重新调度相应任务。

长期运行的服务有 **复制模式（Replicated）** 和 **全局模式（Global）** 两种。Replicated 模式下，manager 在符合约束的节点上维持指定数量的任务副本，多个副本可以部署在不同节点上。Global 模式下，每个符合调度约束的可用节点上都运行一个任务，常用于节点级代理或监控组件，例如每个计算节点都需要一个日志收集器或监控器。

假设一个服务定义了 3 个副本，初始调度后两个副本在 worker 节点、一个在 manager 节点。如果某个 worker 节点失效，实际副本数降为 2，Swarm manager 会检测到差异并自动重新调度一个新副本，将其部署到 manager 或另一个可用节点上，最终恢复到 3 个副本的期望状态。这种自动协调持续进行，无论容器故障、节点不可用还是其他异常，manager 都会将实际状态尽可能拉回期望状态。

### 路由网格与负载分发

Swarm 还提供服务发现机制：为服务提供 DNS 名称，可通过 VIP 或 DNSRR 发现任务。当服务通过某个网络端口对外发布时，Swarm 的 **路由网格（routing mesh）** 功能使集群中任何一个节点都能在该端口上接受请求，包括没有运行该服务实例的节点。

在典型场景中，三个节点分别具有 `192.168.99.100`、`192.168.99.101`、`192.168.99.102` 的 IP，服务 `my-web` 的两个副本运行在 node1 和 node2 上。所有三个节点都在 8080 端口发布服务，各自通过 swarm load balancer 接收请求。即使 node3 上没有任何 `my-web` 实例，它仍能接受 8080 端口的请求，并将其转发到运行实际服务的节点。当某个节点上的容器实例意外终止后，该节点收到的请求会被自动转发到正常节点上处理，从而提高服务可用性。所有节点间通过 ingress network 互联，实现跨节点的请求路由。负载均衡器还可以根据各容器的繁忙程度分发请求，将流量发往相对空闲的副本，而无需写死 IP 地址。

### Swarm 部署：Stack 文件

与 Docker Compose 类似，Swarm 也支持在清单文件中读取容器配置，包括镜像、端口、存储和网络等，文件格式与 Compose 兼容，称为 stack 文件。部署应用使用 `docker stack deploy --compose-file stack.yaml accounts`，关闭应用使用 `docker stack remove accounts`。

Stack 文件在 Compose 基础上新增了一些集群级配置。示例中除了 `services` 外，还包含 `configs` 和 `secrets` 顶层配置。`configs` 用于注入普通配置文件，如 `plain_config` 指向 `./config/plain.yaml`，以文件形式挂载到服务的 `/config/plain.yaml`。`secrets` 用于管理敏感数据，如 `secret_config` 指向 `./config/secret.yaml`，同样以文件形式挂载。服务通过 `configs` 和 `secrets` 引用这些资源并设置 `mode: 0440` 限制权限。`deploy` 字段中则可以定义 `replicas: 1` 指定副本数。还可以通过 `deploy.placement.constraints` 设置调度约束，例如 `node.role == manager` 将服务部署到 manager 节点。这些 configs、secrets 和 replicas 概念在后续 Kubernetes 学习中会反复出现。

### Lab 1 详细要求

#### 系统总体要求

系统至少包含三个运行组件：前端 `frontend` 提供用户界面，通过 HTTP 调用后端 WebAPI；后端 `api` 实现业务规则、参数校验和数据访问；数据库 `database` 持久化场地与预约数据。技术栈自由选择：后端框架和关系数据库均可自行决定（如 Flask、Spring Boot、Node.js；MySQL、PostgreSQL 等）；前端可用主流框架或原生 HTML/CSS/JavaScript；接口采用 HTTP WebAPI；容器工具使用 Docker；多容器应用使用 Docker Compose v2。

#### 数据实体

场地实体至少包含：场地编号、场地名称、所在位置、可容纳人数、开放时间、场地状态（如开放、停用）。预约实体至少包含：预约编号、场地编号、预约人或预约组织、预约日期、开始时间、结束时间、使用目的、预约状态（如有效、已取消）。

#### 必做业务功能

系统至少支持九项功能：查询场地列表、查询场地详情、创建场地、创建预约、查询预约列表、查询预约详情、取消预约、在创建预约时检查场地时间和输入数据的有效性、拒绝同一场地在同一时间段内的冲突预约。

#### 后端 WebAPI 要求

后端至少提供等价接口，路径可以调整但必须在 README 和实验报告中列出。示例接口包括 `GET /api/venues`、`GET /api/venues/{id}`、`POST /api/venues`、`POST /api/reservations`、`GET /api/reservations`、`GET /api/reservations/{id}`、`DELETE /api/reservations/{id}`，也可以使用 `POST /api/reservations/{id}/cancel` 显式取消。API 应使用 JSON 作为主要请求与响应格式；对必填字段、时间范围和场地状态进行校验；对不存在的场地或预约返回明确错误；对预约冲突返回明确错误；不把异常堆栈直接返回给普通用户；数据必须写入关系数据库，不能只保存在进程内存中；数据库连接信息必须从环境变量或外部配置读取。

建议使用语义明确的 HTTP 状态码：查询或取消成功返回 200 OK；创建成功返回 201 Created；请求参数错误返回 400 Bad Request；资源不存在返回 404 Not Found；预约时间冲突返回 409 Conflict；未处理的服务端错误返回 500 Internal Server Error。

#### 前端要求

前端至少提供以下交互：展示场地列表、查看场地基本信息、创建场地预约、展示预约记录、取消预约、显示预约成功信息、显示时间冲突和参数错误等失败信息。前端必须通过 HTTP 调用后端 API，不直接连接数据库，不在前端实现唯一的预约冲突判断。后端地址应可以通过构建参数、环境配置、反向代理或其他合理方式配置。页面能够完成业务操作即可，不要求复杂 UI。

#### 数据库要求

可自行选择关系数据库；至少包含场地表和预约表；明确主键和场地预约之间的关联关系；提供数据库初始化脚本、迁移文件或框架迁移机制；提供少量可用于演示的场地种子数据；预约数据必须持久化；取消预约可以采用逻辑取消或物理删除，但必须在设计和报告中说明；数据库密码不得写死在源代码或 Docker 镜像中。

#### Dockerfile 要求

前端 Dockerfile 应能独立构建前端镜像，构建产物通过容器提供服务，不把本地依赖缓存和无关文件复制到镜像，合理使用 `.dockerignore`，明确容器监听端口。后端 Dockerfile 应能独立构建后端镜像，最终运行镜像不包含不必要的源码、编译工具和缓存，使用前台进程作为容器主进程，通过环境变量读取数据库配置，不在镜像中写入数据库密码，合理使用 `.dockerignore`，建议使用非 root 用户运行。镜像使用明确合理的基础镜像版本，名称和标签应有含义，不要求推送到公共镜像仓库，但应保证他人能根据源码和 Dockerfile 重新构建镜像。

#### Docker Compose 要求

项目根目录或 `deploy/` 目录中应提供 `compose.yaml`，至少定义 `frontend`、`api`、`database` 三个服务。服务要求：`frontend` 使用前端镜像，对外发布访问端口，能够访问 `api`，不直接访问 `database`；`api` 使用后端镜像，通过 Compose 服务名连接数据库，从环境变量或外部配置读取数据库信息；`database` 使用标准数据库镜像，通过环境变量配置数据库名、用户名和密码，使用命名 Volume 或绑定目录持久化数据，配置合理的 healthcheck。

网络要求：前端、API 和数据库通过 Compose 网络通信；API 使用服务名连接数据库；只有确需从宿主机访问的端口才对外发布；数据库端口原则上不必对外发布，如开发调试需要发布应在报告中说明。配置要求：普通配置可放入 `compose.yaml` 的 `environment`、`.env`、`env_file` 指定的文件或应用支持的外部配置文件；不得在 Dockerfile 中写入环境相关密码。

#### 运行与验收要求

基本功能验证至少完成：打开前端页面、查询场地列表、创建正常预约、查询刚创建的预约、创建时间冲突的预约并确认后端拒绝、取消预约、在取消后的时间段重新创建预约并确认结果符合设计。容器验证需执行 `docker compose up --build -d` 和 `docker compose ps`，确认容器状态正常，并验证数据持久化效果。
