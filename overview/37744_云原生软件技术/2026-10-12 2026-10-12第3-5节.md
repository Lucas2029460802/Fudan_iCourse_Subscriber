### Docker 基础实践

本次课的教学目标是从理论过渡到实操。上一讲已经从理论层面讨论了容器存在的原因和背后的关键 Linux 内核机制，本次课则重点让每位同学在自己的电脑上完成 Docker 环境的安装与基本镜像、容器的操作。教师强调，当前部分同学可能在简历或项目中使用过 Docker，但大多只停留在最基本的命令层面，因此本课从最基础的镜像化命令和容器命令出发，通过一个简单的 sender-receiver 双容器示例，让大家完整体验“编写代码 → 编写 Dockerfile → 构建镜像 → 运行容器 → 查看日志 → 停止与删除容器”的流程。

在理论层面，容器本质上依赖 Linux 内核中的三类核心机制。第一类是 **namespace（命名空间）**，它按照逻辑维度对系统资源进行划分，同一个命名空间中的资源归一个容器使用，从而无法访问其他命名空间中的资源。这属于逻辑隔离而非硬件级隔离，与虚拟机相比隔离性较弱，但在常规使用场景中问题不大。第二类是 **Cgroup（控制组）**，当一台服务器上运行大量容器时，必须对每个容器的资源使用设置上限，包括内存、IO、CPU 等，避免单个容器耗尽整机资源从而影响其他容器。第三类是**联合文件系统（UnionFS）**，容器的文件系统以分层形式堆叠，底层为基础镜像层，只有最顶层是可写层（writable layer）。容器镜像中不包含操作系统内核，因此体量远小于虚拟机镜像：虚拟机镜像动辄数 GB，而容器镜像通常只有几百 MB，简单镜像甚至几 MB 即可。

### Docker Desktop 安装与验证

从学习角度出发，第一步是下载 Docker Desktop。安装包可以从官方文档地址 `https://docs.docker.com/get-started/get-docker/` 获取，根据操作系统选择对应版本。安装完成后，在 PowerShell 或终端中运行 `docker version` 命令，若能正常输出 Client 和 Server 两部分信息，则说明 Docker 指令环境已就绪。Docker 在架构上包含 **Client** 和 **Server** 两个核心组件，Client 负责接收用户命令，Server（即 Docker Engine）负责实际的镜像管理和容器运行。

验证安装的最简单方式是执行 `docker run hello-world`。这个命令背后实际包含了两步操作：首先从 Docker Hub 远程仓库拉取 hello-world 镜像，然后基于该镜像实例化一个容器并运行。hello-world 是官方提供的最小测试镜像，运行成功后会在终端输出 "Hello from Docker!" 等确认信息。在 Windows 上安装 Docker Desktop 时，系统会自动安装 WSL2 虚拟环境作为后端。因此如果安装后容器无法正常启动，首先应当检查 WSL2 是否已启用且运行正常。微软官方 WSL 文档地址为 `https://learn.microsoft.com/zh-cn/windows/wsl/install`。

Docker Desktop 本身是一个图形化 UI 界面，许多操作可以不必通过命令行完成。界面中最重要的几个栏目包括：**Images** 展示本地已拉取的所有镜像，包含名称、Tag（版本标签）、Image ID（自动生成的随机字符串）、Created（拉取时间）、Size（大小）以及可执行的 Actions；**Containers** 展示当前正在运行或被停止的容器列表；**Volumes** 展示容器外挂的存储空间；**Kubernetes** 栏表明当前 Docker Desktop 已集成 K8S 能力，后续课程会涉及；**Logs** 则用于查看容器运行过程中输出的日志。

### Docker Hub 与国内镜像配置

本课程讲解和使用的容器均为 **Linux 容器**。由于 Linux 容器依赖 Linux 内核，在 Windows 或 macOS 上运行 Docker 时，实际上是先启动一个 Linux 虚拟机，再在该虚拟机内部运行 Linux 容器。目前 Docker Desktop 默认使用 WSL2 作为虚拟机后端，不建议使用 Hyper-V。

Docker 官方的远程仓库 Docker Hub 在国内通常无法直接访问，需要配置国内镜像仓库（mirror）。当前大陆境内可用的 Docker 镜像状态可以通过在线监控页面查询（如 `https://status.anye.xyz/status/docker`），其中列出了如 1Panel 官方、CloudFlare 等提供的镜像地址。配置方式是在 Docker Desktop 的 Settings → Docker Engine 中，在 JSON 配置文件中添加 `registry-mirrors` 数组，将可用的镜像地址填入。可以同时配置多个镜像源，Docker 会按顺序尝试拉取。

### Docker 镜像交互命令

镜像相关的基础命令包括 `docker search`、`docker pull`、`docker images`、`docker tag` 和 `docker rmi`。

`docker search` 用于在远程仓库中搜索镜像。例如执行 `docker search python` 会返回大量与 Python 相关的镜像列表，包括名称、描述、星标数和是否为官方镜像等字段。Python 官方基础镜像体积相当大，完整版本可能达到数百 MB 甚至超过 1GB，在课堂网络环境下下载会非常缓慢，因此建议使用 `python:3.12-slim` 这类压缩版本的小镜像。

`docker pull` 用于从远程仓库拉取镜像，命令格式为 `docker pull [OPTIONS] NAME[:TAG|@DIGEST]`。冒号后面的 TAG 表示版本标签，如果不指定则默认拉取 `latest` 标签。`docker images` 用于查看当前本地已存在的所有镜像，输出包括 REPOSITORY（仓库名）、TAG、IMAGE ID、CREATED 和 SIZE 等信息。

`docker tag` 用于为镜像打标签，方便版本管理。例如将一个 Python 镜像标记为 `my-python:v1`，这样同一镜像就可以拥有多个不同的标签引用，避免同名镜像之间相互覆盖。`docker rmi` 用于删除本地镜像，但有一个前提条件：如果该镜像已经有正在运行的容器，需要先删除相关容器，然后才能删除镜像本身。

### Docker 容器运行命令

将镜像实例化为容器的核心命令是 `docker run`，其中包含多个高频使用的参数。

`-i` 参数表示交互式操作，允许用户在命令行终端中与容器进行交互；`-t` 参数表示分配一个终端（TTY），二者通常组合为 `-it` 使用。`-d` 参数即 detach 模式，使容器在后台持续运行而非占用当前终端。与容器功能密切相关的另外两个参数是 `-v` 和 `-p`。`-v` 用于文件挂载，将容器内的某个目录映射到宿主机操作系统中的具体目录，因为容器中的存储本质上落在宿主机的文件系统中，通过映射可以搭建容器与宿主机的存储关联，实现数据持久化。`-p` 用于端口映射，将容器内部的端口映射到主机的端口。例如外部应用通过访问主机的 8080 端口，该请求会被转发到容器内部的 8081 端口。

以交互模式运行 Python 容器的示例为：`docker run -it python`，进入容器后执行 `python --version` 可以看到 Python 版本信息，输入 `exit` 退出容器。

查看容器的命令是 `docker ps`，加 `-a` 参数可查看所有容器（包括已停止的），输出包含 CONTAINER ID、IMAGE、COMMAND、CREATED、STATUS、PORTS 和 NAMES 等字段。`docker start` 用于启动已退出的容器，与之对应的是 `docker stop` 用于关闭运行中的容器。stop 只是将容器停止挂起，并未将其删除，之后可以通过 start 重新启动。删除容器使用 `docker rm`，但如果容器处于 running 状态，直接删除会报错，需要先 stop 再 rm，或者使用 force 参数强制删除。进入已运行容器内部执行交互式操作使用 `docker exec -it`，例如 `docker exec -it 749bc4c9c5aa /bin/bash` 可以进入指定容器的 shell 环境。

### Dockerfile 基础

Dockerfile 是构建镜像的核心配置文件，它是一个文本文件，包含一条条构建镜像所需的指令和说明。利用 Dockerfile 可以构建自定义镜像并保存在本地，之后通过 `docker run` 等命令将其运行为容器。

Dockerfile 中常用的指令包括：`FROM` 指定基础镜像；`RUN` 在基础镜像上执行命令，这些命令在构建镜像时执行，每一行命令都会在镜像上新增一层；`COPY` 将主机目录中的文件拷贝到镜像目录中；`EXPOSE` 声明镜像暴露的端口，仅作为配置说明，真正意义上的端口映射需要在 `docker run` 时通过 `-p` 参数完成；`WORKDIR` 指定容器内的工作目录；`ENTRYPOINT` 定义容器启动时执行的命令；`CMD` 提供默认参数或默认命令。当 ENTRYPOINT 与 CMD 同时存在时，CMD 中的内容会作为参数追加到 ENTRYPOINT 指定的命令之后；若没有 ENTRYPOINT，CMD 则直接作为容器启动时执行的命令。

一个典型的 Python 容器 Dockerfile 示例为：

```dockerfile
FROM python:3.12-slim
COPY . /app/sender
WORKDIR /app/sender
RUN pip3 install requests
EXPOSE 8080
ENTRYPOINT ["python"]
CMD ["sender.py"]
```

通过该 Dockerfile 构建镜像的命令为 `docker build -t sender:v1 .`，其中 `-t` 参数给镜像添加 Tag，`sender` 为镜像名称，`v1` 为 Tag 名，最后的 `.` 表示 Dockerfile 位于当前目录，这个点不能省略。构建完成后可以通过 `docker images` 查看新生成的镜像。

### 双容器示例：sender 与 receiver

本次课的实践环节使用一个简单的双容器应用。sender 容器运行一个 Python 客户端脚本，在 `while True` 无限循环中持续向 receiver 容器发送 HTTP 请求，目标地址为 `http://receiver:8081`，其中 receiver 是容器在自定义网络中的名称。发送请求后获取 response 并记录；如果 receiver 不可用，会在日志中输出 error 信息，并每隔 1 秒重试。receiver 容器运行一个 HTTP 服务器，基于 `socketserver.TCPServer` 监听 8081 端口，处理来自 sender 的请求。它的处理逻辑是获取请求路径参数，构建响应内容字符串，设置响应状态码 200 和响应头，将响应信息写入本地文件，并将响应发送给客户端。

两个容器各自拥有独立的 Dockerfile。sender 的 Dockerfile 基础镜像使用 `python:3.12-slim` 以减小下载体积，由于代码中包含 `import requests`，在构建时需要通过 `RUN pip3 install requests` 安装依赖。receiver 的 Dockerfile 结构类似，但不含 requests 依赖，暴露的端口是 8081。

在实际操作流程中，首先进入 sender 目录执行 `docker build -t sender:v1 .` 构建镜像。构建过程中的日志会依次显示 FROM、WORKDIR、COPY、RUN 等各步骤的执行情况。然后通过 `docker network create mynet` 创建自定义网络，使后续加入该网络的容器之间可以通过容器名称互相通信。已有的网络再次创建会报错，这在本地环境中是正常现象。

接着运行 sender 容器：`docker run -d -p 8080:8080 --network mynet --name sender sender:v1`。此处在 sender 场景中不需要 `-v` 挂载，因为应用不需要持久化存储。由于此时 receiver 尚未启动，通过 `docker logs -f sender` 查看日志会发现持续的连接错误。使用 `docker stop sender` 可以停止容器，此时容器状态从 Up 变为 Exited；再通过 `docker start sender` 可以重新启动。若在 running 状态下直接 `docker rm sender` 会报错，提示需要先停止容器。

在 receiver 目录中执行 `docker build -t receiver:v1 .` 构建镜像，然后运行 `docker run -d -p 8081:8081 --network mynet --name receiver -v $pwd/file:/file receiver:v1`。这里的 `-v` 参数将当前目录下的 file 文件夹映射到容器内的 /file 目录，作为响应日志的持久化存储位置。当 receiver 启动后，再查看 sender 的日志，可以看到正常的响应信息，包括宿主机 IP、时间戳和 200 状态码；查看 receiver 日志则能看到不断累积的请求记录，这些记录会持续写入映射的文件中。

### 容器编排的引入

从单容器管理过渡到多容器编排，是本节内容的核心逻辑。Docker Compose 的定位是在本地单机环境中管理多容器应用，而 Docker Swarm 则是早期 Docker 官方的多节点集群编排方案，如今基本已被 Kubernetes 取代。理解编排的定义是一切的基础：**编排（orchestration）** 在计算机领域指的是以自动化方式配置、协调和管理系统。这个词容易让人产生误解，以为是指像编排舞蹈一样设计顺序流程；实际上在云原生语境中，编排更强调自动化控制、协调和管理，而非简单的顺序连接。

容器编排的任务包括：自动完成容器化工作负载的部署、网络配置、存储管理、伸缩扩容和生命周期管理。工作负载不仅指基本的 container，还包括 Kubernetes 环境中的 Deployment、Job 等更高级的抽象。容器在扩容场景中的优势尤为明显，因为容器可以秒级启动，而虚拟机需要分钟级启动，这使容器成为应对高并发流量时快速横向伸缩的理想载体。

容器编排的第二个重要价值是**减少重复的手工操作**。当应用只涉及两三个容器时，手工执行 `docker build`、`docker run` 等命令完全可行；但当应用包含十几个甚至几十个容器，且需要在多个用户环境中重复部署时，手工操作将变得极其耗时且容易出错。将所有容器的部署配置集中在一个命令文件中，每次部署只需执行一条命令，是容器编排要解决的核心问题。

### 多容器应用的现实需求

真实应用中，一个完整的系统通常由前端界面、后台 API、数据库、缓存等不同职责的组件共同组成。技术上将整个应用打包进单一容器是可行的，但从管理角度存在明显问题：将职责不同的组件放在同一容器中会降低独立部署、扩缩容和故障隔离的能力。单体的扩容是整体扩容，无法针对高流量的关键服务（如后台 API）进行精确扩展，而其他低频使用的组件则会被一并冗余扩容，造成资源浪费。拆分为多个容器化服务后，各个服务可以独立部署、独立升级、独立伸缩，也可以根据各自的资源需求灵活调度到不同节点上。

多容器服务之间存在**网络和数据依赖**。一个典型的例子是应用服务依赖数据库服务：应用启动时需要从数据库读取配置参数，才能正确完成初始化。这里的核心问题是：**容器创建的顺序不等于服务就绪的顺序**。即使数据库容器已经启动，数据库软件本身可能还需要数秒到数十秒的初始化加载时间才能真正对外提供服务。如果此时应用容器立即启动并尝试连接数据库，就会因为数据库尚未就绪而出错。因此，编排工具需要处理两个层面的顺序：容器启动顺序和容器内部服务的就绪状态。

为解决这一问题，Compose 提供了 `depends_on` 字段来声明服务之间的依赖关系，确保被依赖的容器先启动；但仅靠依赖顺序还不够，还需要结合 **health check** 机制来判断服务是否真正就绪，只有在前置服务通过健康检查后才启动后续容器。这正是多容器应用自动化配置与管理的典型场景。

### 声明式配置与编排价值

手工维护多条 Docker 命令存在显著缺陷：构建、镜像配置和部署流程在不同环境中可能出现不一致；管理复杂度随服务数量增加而急剧上升；未经审查的手工操作在生产环境中风险较高。容器编排通过**声明式配置**和自动化流程应对这些问题。声明式配置的含义是：用户不指定每一步的具体操作步骤，而是声明期望达到的目标状态，由编排系统自动执行操作以达成该状态。Docker Compose 和 Kubernetes 都采用这种声明式模式。

在 Docker 生态中，容器编排的核心工具是 **Docker Compose**。它读取一个配置文件（类似于 Dockerfile 之于单个容器），该文件中定义了应用模型中的服务、网络和存储资源。Compose 的配置文件默认文件名为 `compose.yaml` 或 `compose.yml`（两者等价，早期文件系统扩展名只有三位的历史原因导致 `.yml` 至今仍被广泛使用，旧版名称 `docker-compose.yml` 也仍受支持）。YAML 是一种轻量级的数据组织格式，通过缩进来表达层次关系，可以描述对象和数组等结构。

### Docker Compose 的边界与定位

Compose 有一个重要约束：它主要管理**单个 Docker Engine** 上的资源，面向单机环境，**不提供多节点集群调度**。这意味着 Compose 编排的所有容器必须运行在同一台服务器上。对于真正的分布式应用，不同服务需要部署在不同计算节点上，这些节点组成集群，此时 Compose 无法承担集群级调度，需要借助 Docker Swarm 或 Kubernetes。对本课程而言，Lab 实验的场景均在本地单机环境完成，Compose 已经完全够用。

Compose 内部包含两个核心概念。**服务（Service）** 是对一类容器的镜像、命令、端口、网络和存储等运行配置的抽象定义，是应用的一个组成部分。**项目（Project）** 是一组相关联的服务和资源组成的应用单元，由一个或多个 Compose 文件定义，通常情况下一份 Compose 文件就定义一个项目。Compose 的抽象层次高于单个 Docker 容器：它以项目为管理边界，统一管理项目中所有容器的生命周期。

在没有 Compose 的情况下部署多容器应用，需要逐条手工执行 `docker run` 命令，手动维护依赖关系和启动顺序。例如启动 MySQL 数据库时需要传入 `-e` 环境变量参数指定 root 密码和数据库名，再启动 WordPress 前端服务。有了 Compose，只需在 `compose.yaml` 中定义各服务，一条 `docker compose up` 命令即可完成所有容器的创建和启动。

### Docker Compose 基本命令

`docker compose up` 是启动应用的核心命令。它的作用包括构建（可选）、创建、启动并连接 Compose 文件中定义的服务容器。首次执行时根据 Compose 定义创建并启动容器；后续重复执行时，如果已有容器且配置或镜像未发生变化，通常复用已有容器；如果配置或镜像发生变化，则停止并重新创建受影响的容器，同时保留已经挂载的卷。参数 `--force-recreate` 可以强制重建所有容器。在前台模式下，Compose 会聚合输出各服务的日志，便于观察启动过程；加 `-d` 参数则转为后台运行。

`docker compose down` 用于停止并删除项目中的服务容器和 Compose 创建的网络。默认情况下，容器和网络会被删除，但镜像不会被删除（除非指定 `--rmi` 参数），命名卷和匿名卷也不会被删除（除非指定 `-v` 或 `--volumes` 参数）。这种设计在开发环境中很有实用价值：关闭并清理容器环境的同时，保留持久化数据，便于下次启动时继续使用。但教师特别提醒，使用 `-v` 删除卷时必须谨慎，需确认数据用途或做好备份。外部卷（external volumes）和外部网络即使指定删除参数也不会被移除。

`docker compose start` 用于启动项目中已存在但处于停止状态的服务容器。与 `up` 的关键区别在于：start 不会根据 Compose 文件重新创建容器，也不会应用新的配置或镜像变化。它仅启动已被停止的已有容器，不持续聚合日志，在后台启动后立即返回终端。使用场景是快速恢复之前通过 Compose 创建并停止的容器。若需要应用配置变更，应使用 `up` 而非 start。

`docker compose stop` 与 start 对应，用于停止正在运行的服务容器但保留容器本身，不删除容器、网络或卷。它会向容器发送停止信号，超时后强制停止。使用场景是临时暂停服务，例如维护前暂停应用，之后用 start 恢复同一批已有容器。这两组命令的关系与单个 Docker 容器中的 `docker stop` 与 `docker start` 完全类似，只是作用范围从单容器扩展到整个项目级别。
