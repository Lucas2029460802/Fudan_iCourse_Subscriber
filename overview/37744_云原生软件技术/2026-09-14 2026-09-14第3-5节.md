### 现代软件行业的需求

现代软件行业面临的核心压力可以归纳为三个方面。首先是**上线交付时间越来越短**，业务方希望应用能够快速迭代、快速上线，抢占市场窗口。其次是**设备形式越来越多样化**，应用不仅需要在 PC 浏览器上运行，还需要覆盖手机原生应用、微信小程序、平板甚至各种智能硬件终端的展示与交互。以手机端为例，iOS 与 Android 两大操作系统必须同时支撑，未来在国内还需要考虑鸿蒙系统。Android 生态的碎片化问题尤为突出，不同厂商、不同分辨率、不同屏幕尺寸导致前端展示与兼容性测试的工作量显著增加。第三是**服务可靠性要求越来越高**，尤其在一些关键领域如船舶机电系统、智能硬件设备中，软件能否持续稳定运行直接关系到业务安全。

为应对这些需求，软件行业需要一个全新的软件架构与开发方式，同时需要更加完善的程序设计理念和更强大、灵活的计算基础设施。具体而言，现代应用需要具有容错性好、易于管理、便于观察的松耦合系统，以保证服务的高可靠性。这些需求自然引出了云原生技术——它正是应对上述挑战的一套完整工程体系和技术手段。

### 软件架构的历史演进

#### 从单体架构到云原生

软件架构并非一成不变，而是随着技术迭代不断演进。主流架构形态的演进路线大致为：**单体架构 → 面向服务架构（SOA）→ 微服务架构 → 云原生架构**。需要注意，这种演进不是单向替代关系，单体、SOA 与微服务在实际工程中长期共存。选择哪种架构，应综合考虑业务复杂度、团队规模、可靠性目标和交付节奏。例如，一个功能简单、并发压力小的内部管理系统，用单体架构完全够用，过度拆分反而增加开发和运维成本。

#### 单体架构的特点与局限

单体架构是将所有功能模块作为一个整体构建和部署。经典的单体应用采用三层分层设计：**展现层、业务层和持久层**。展现层负责与客户端交互，业务层处理具体业务逻辑，持久层负责数据访问。早期 Java Web 开发中的 SSH 框架组合（Struts + Spring + Hibernate）正是这种分层思想的典型体现：Struts 负责 HTTP 请求转发，Spring 承载业务服务层，Hibernate 提供对象关系映射（Object-Relational Mapping），将数据库表映射为对象，用对象的增删改查操作替代手写 SQL。前端则通过 JSP 或 HTML 页面配合 JavaScript 与 AJAX 实现局部渲染和交互。

单体架构的项目结构简单，对于小型应用非常实用。但随着业务越来越复杂，单体应用的规模不断膨胀，编译时间变长，部署也越来越困难。最核心的缺陷在于：任何一个局部的错误都可能导致整个应用不可用。例如，访问 Web 应用时常见的 503 或 500 错误，往往就是后台某个环节异常导致全站宕机。因此，当系统规模超出一定阈值后，必须有意识地进行拆分和解耦。

#### SOA 的核心思想与 ESB 的瓶颈

面向服务架构（SOA）的核心在于将应用程序中的不同功能单元拆分成不同的服务，服务之间通过接口或规定的协议进行通信。SOA 强调围绕**可复用服务**和**标准契约**组织系统：服务对外暴露规范化的接口描述，其内部实现被隐藏，调用方只需理解接口即可进行访问。这体现了软件工程中的信息隐藏与模块化原则。

SOA 的一种典型集成方式是**企业服务总线（ESB）**。ESB 提供路由、转换、协议适配与治理能力，适合复杂的企业级系统集成场景。在 2000 年代，企业内部往往存在多条业务线的多个孤立应用系统，ESB 允许这些系统通过统一的协议和路由机制相互协作，而不必推倒重建。但 ESB 的显著缺点是：当业务逻辑或治理能力过度集中到总线时，ESB 本身会成为性能瓶颈、变更瓶颈或较大的故障域。老师用上海南北高架的拥堵做了类比——所有车流汇聚到主干道上，最终导致整体效率下降。

#### 微服务架构

微服务架构将系统中的每一个服务视为一个**独立的可部署单元**。服务之间相互解耦，通过远程通信协议进行协作，整个系统呈现分布式形态。微服务与 SOA 有一定继承关系，但内涵更为丰富：每个服务有独立的团队、独立的测试流程、独立的数据存储和独立的部署节奏，服务可以部署在不同的服务器节点上。

与此同时，微服务架构也引入了分布式系统的内生复杂性。由于服务数量众多且通过网络通信，必须配套解决**服务注册与发现、统一配置中心、链路追踪**等治理问题。还需要考虑 API 网关、熔断器等基础设施组件。分布式系统的复杂性还包括 CAP 定理（一致性、可用性、分区容错性三者最多同时满足两个）与 BASE 原则等基本约束。

#### 微服务向云原生架构的演化

随着容器技术、容器编排尤其是 Kubernetes 的成熟，以及云计算的逐步落地，微服务架构在交付周期和服务可靠性上获得了进一步提升。容器、声明式 API、自动化编排和云平台能力使应用更容易实现**可移植交付、弹性伸缩与自愈**。在微服务架构中原本需要大量手动处理的非业务层面治理问题，逐渐被容器平台和配套工具以产品化方式解决。软件架构由此逐步演化为云原生架构。

需要特别指出的是，云原生平台**不会消除分布式系统的复杂性**，分布式系统固有的延迟、部分失败、一致性和可观测性问题依然存在。云原生的价值在于帮助团队以一致化的方式来管理这种复杂性，使其可控、可预期。

### 云原生的概念与本质

#### 概念起源

云原生（Cloud Native）一词由 Cloud 和 Native 组合而成。2013 年，Pivotal 的 Matt Stine 系统讨论了云原生应用思想，涵盖 **DevOps、持续交付、微服务和敏捷基础设施**。其核心主张是应用程序从设计之初就考虑云的环境，为云而设计，在云上以最佳方式运行，充分利用云平台的弹性和分布式优势。

云原生的关键在于**利用自动化、弹性、分布式与按需资源**，同时**接受并治理部分失败**。所谓“接受并治理部分失败”，意味着不再试图完全杜绝故障，而是假设故障必然发生，通过自动化机制实时感知故障并快速恢复。例如，一个容器实例崩溃后，Kubernetes 可以自动重新启动替换实例；一个节点因硬件故障不可使用时，平台可以将该节点上的容器迁移到其他健康节点重新运行。这种自愈能力对使用者透明，无需人工干预。

云原生架构中，应用面向云设计，生在云上、长在云上。在故障发生时可以实现应用服务能力的自我恢复，依托容器技术可以实现快速的弹性伸缩。这一架构最终服务于现代软件行业的三大需求：缩短上线交付时间、支持多样化设备、提高服务可靠性。

#### 云原生发展历程

云原生的技术基础可以追溯到 2001 年的虚拟化技术，如 VMware 等虚拟化产品的出现。2006 年，亚马逊推出 AWS（Amazon Web Services），标志着 IaaS（Infrastructure as a Service）云计算的起步，用户可以通过租用方式获取基础设施资源。此后，Heroku 等平台推动了 PaaS（Platform as a Service）的发展，使开发者在云上完成开发和部署。2009 至 2010 年间，OpenStack 等开源 IaaS 项目出现，企业可以在自有服务器上构建云环境，实现按需资源调度和伸缩。

2013 年是云原生的关键时间节点：云原生概念被正式提出，Docker 容器技术随之发布。Docker 并非全新发明，它基于 Linux 内核已有的 cgroup 和 namespace 等沙箱隔离机制进行了更友好的封装和产品化。2014 年 Kubernetes 正式发布，为容器编排提供了统一的平台方案。2015 年，在谷歌倡导下成立云原生计算基金会（CNCF），Kubernetes 成为 CNCF 的第一个孵化项目。

#### CNCF 与云原生生态

CNCF 是一个厂商中立的基金会，致力于推动开源云原生技术的推广和普及。其使命是通过培养和维持一个开源、供应商中立的项目生态系统，实现“让云原生无处不在”的愿景。2018 年，CNCF 对云原生进行了重新定义：云原生技术有利于各组织在公有云、私有云和混合云等新型动态环境中构建和运行可弹性扩展的应用。云原生的代表技术包括**容器、服务网格、微服务、不可变基础设施和声明式 API**。这些技术能够构建容错性好、易于管理和便于观察的松耦合系统，并结合可靠的自动化手段，使工程师能够轻松对系统做出改进和可预测的重大变更。

从最初只有 Kubernetes 一个项目，CNCF 生态已经扩展到上千个开源项目，覆盖应用定义与镜像构建、持续集成与交付、调度与编排、服务网格、API 网关、协调与服务发现、远程过程调用、云原生存储、云原生网络、容器运行时、安全与合规、自动化配置、可观测性、混沌工程等众多领域。其中比较有代表性的项目包括：镜像仓库 Harbor、CI/CD 工具 Argo 与 Flux、服务网格 Istio 与 Linkerd、API 网关 Envoy 与 Kong、容器运行时 CRI-O 与 kata、可观测性工具 Prometheus、Fluentd、OpenTelemetry，以及混沌工程工具 ChaosMesh 等。CNCF 全景图（Landscape）已经成为了解云原生技术生态的重要入口。

### 云原生核心技术与实践

云原生技术与实践可以从五个维度来概括：架构设计原则是**解耦**，应用交付手段是**封装**，架构特征或运行结果是**高可扩展的分布式**，开发方法是**敏捷开发**，软件交付实践是**持续部署**。

#### 解耦

从大型机、服务器到虚拟机（VM）、再到容器，资源分配的颗粒度越来越小，启动速度越来越快，资源重建的代价越来越小。这背后都是解耦思想的体现。单体应用把所有功能耦合在一起，交付困难、协同复杂。云原生强调**分而治之**，将应用分解为高内聚、松耦合的模块，模块之间通过远程 API 协作。这种解耦原则的核心是**高内聚、低耦合**，与软件工程中模块化设计的要求一致。

解耦后的系统呈现分布式形态：业务被拆分为多个独立的 service，服务之间通过远程调用协作。每个服务可以独立开发、独立部署，一个服务的故障不会直接拖垮其他服务，这是运行时容错能力的重要基础。至于如何拆分服务，后续课程会介绍面向业务对象拆分和领域驱动设计（DDD）两种策略，这两种策略虽有相似之处，但在本质上有区别。

#### 封装

云原生应用交付的核心手段是将**应用与环境封装在一起，同时发布**。传统部署中，同一应用在不同服务器上可能面临环境不一致的问题：有的服务器安装了不同版本的依赖库，有的缺少必要的系统组件，导致部署成功与否取决于目标机器状态。云原生通过容器镜像将应用的代码逻辑、依赖项、系统库全部打包，部署时对外界环境几乎无依赖，只需提供基础操作系统即可。

与此同时，云原生平台通过 API、声明式配置和基础设施即代码（IaC，Infrastructure as Code）管理计算、网络、存储等资源，使基础设施具备自助申请、快速交付、版本控制、自动验证和可重复创建的能力。具体包括：**自助服务**，开发团队通过平台或 API 获取环境而不必经人工审批；**声明式管理**，描述期望状态，由系统自动完成协调，而非编写命令式脚本来操作资源；**版本控制**，基础设施配置可审查、可追踪；**可重复创建**，不同环境采用一致的自动化流程；**自动验证**，基础设施配置可检查、测试和审计，并且支持快速回滚或替换。

#### 高可扩展的分布式

云原生系统本质上是一个分布式系统，由多个独立计算节点通过网络协作，对外提供统一能力。分布式系统对用户和开发者而言，在中间件（Middleware）的屏蔽下，看起来像一台机器在工作，但其底层由一组独立机器组成。分布式中间件的重要价值在于屏蔽网络地址、地理位置等差异。例如，服务 A 调用服务 B 时，在传统方式下必须预先知道 B 的 IP 地址和端口；而在云原生环境中，A 通过服务名称发起调用，由平台自动完成服务发现和请求路由。即使服务 B 所在节点发生变化，A 也无需修改任何配置。

这种机制的本质是将服务发现与路由从应用代码中剥离，交给平台处理。这带来显著的灵活性：服务 B 可以有多个副本部署在不同节点上，A 的请求由哪个副本处理对 A 透明。在这个例子中，服务 B 的 IP 地址可能今天指向 192.168.0.1，明天因为节点故障迁移到 192.168.0.2，但 A 的逻辑不受影响。

分布式系统的优势在于可以将计算任务分配到不同机器上，提升**横向扩展、故障隔离和资源利用**能力。通过多副本部署和负载均衡，海量请求可以被平均分配到多个实例上，整体响应时间下降，性能得到提升。同时，不同实例之间的故障不会相互影响。但分布式系统也引入了**延迟、部分失败、一致性与可观测性**问题。其中，可观测性问题是云原生运维中的核心关注点之一：如果不对分布式系统进行跟踪，就很难快速定位故障发生的位置。

#### 敏捷开发、CI/CD 与 DevOps

云原生的开发方法强调快速、频繁地升级应用程序而不影响业务服务。**敏捷开发**关注开发过程，强调的是变化，效果是加速开发。在用户需求频繁变更的环境下，敏捷方法通过将任务拆分为短周期的迭代（例如一两周甚至两三天）来快速应对变化。**CI/CD（持续集成与持续交付/持续部署）**关注软件定义的软件工作，强调的是工具的使用，效果是自动化。典型的 Jenkins 流水线可以在代码提交后自动触发构建、代码检查、单元测试、集成测试和发布等环节。**DevOps** 关注的是文化，强调的是角色的融合，效果是快速响应能力。它将开发（Development）和运维（Operations）合体，打破专业壁垒，使团队对从开发到运行的整个生命周期负责。

三者的侧重点不同，但共同目标是一致的：在不牺牲安全与可靠性的前提下，提高交付速度和反馈质量。需要区分持续交付（Continuous Delivery）和持续部署（Continuous Deployment）两个概念：持续交付保证可以持续产出可发布的制品，但部署环节可能仍需人工触发；持续部署则将部署环节也自动化。

#### 云原生技术体系的四大组成部分

云原生技术体系由四个主要部分组成。**容器**方面，Docker 是应用与依赖封装在一起的载体，是微服务发布的最佳单位。容器具有轻量化、启动快、高效低耗的特点，适合由 Kubernetes 进行编排管理。**微服务**方面，每个服务是单一职责的业务模块，通过远程网络调用协作，每个服务可独立部署、更新、扩容和重启。代表性技术栈包括 Spring Cloud、Service Mesh 等。**DevOps** 关注整体价值交付效率而非单独的开发或运维，打通专业壁垒，强调度量驱动开发（MDD），注重可视化、量化和自动化。**持续交付**要求把系统看成产品而非项目，实现快速发布、快速反馈、频繁发布，打通业务与 IT 闭环；自动化部署策略包括蓝绿部署、金丝雀部署和灰度发布等。代表性工具包括 Jenkins 用于持续交付流水线、Git 用于版本控制、Ansible 用于自动化运维和配置管理。

### 容器：云原生的计算环境

容器是云原生的最佳封装器。它是一种**轻量化的虚拟化技术**，基于操作系统内部的应用隔离实现不同容器之间的隔离。容器的启动速度非常快，通常小于 1 秒。程序、环境、依赖项、系统库都封装在容器内部，以**容器镜像（Image）**为单元进行部署，对环境基本无依赖，因此容易实现跨平台部署。

与虚拟机相比，容器具有良好的隔离性，但隔离强度相对较弱——容器的隔离发生在操作系统层面，而虚拟机的隔离发生在物理层，因此理论上容器更易被突破。容器的成本远低于虚拟机：一台服务器上通常只能运行十几台虚拟机，而容器可以部署几百甚至上千个。在部署密度上，容器具有显著优势。

容器技术不仅仅包括 Docker 和 Kubernetes，还涵盖容器存储、容器网络、容器 GPU、容器 HPC（高性能计算）、容器边缘计算等方向。在容器化部署演进过程中，部署形态经历了从**传统部署**（硬件 + 操作系统 + 框架 + 应用）到**虚拟化部署**（硬件 + 操作系统 + Hypervisor + 多个 VM），再到**容器化部署**（硬件 + 操作系统 + 容器平台 + 多个容器），最终到 **Kubernetes 部署**的演变。Kubernetes 部署的关键差异在于自动化：用户只需声明期望状态，K8s 平台自动拉取镜像、实例化相应数量的容器副本，并持续跟踪和管理容器的运行状态。

#### Kubernetes 的编排能力

Kubernetes 是容器编排引擎，其核心能力包括：在节点上创建和部署容器；进行资源管理，把容器部署到有足够资源的节点上，或者当节点超出限额时将容器转移到别的节点；监控容器运行状态，出现故障时重启或重新编排；在集群内对容器自动扩缩容；为容器提供网络映射服务和负载均衡服务。

资源管理是 K8s 的关键功能之一。容器在声明定义时可以指定资源要求，例如至少需要 200 兆内存和 0.5 个 CPU 核心。K8s 会根据这些要求将容器调度到具有足够资源的节点上，而不会被放置到可用内存不足的节点上导致运行失败。当某个节点上的资源被其他高消耗服务挤占，导致容器资源不足时，K8s 可以将该容器迁移到资源更充裕的节点上。在集群内，K8s 可以实现自动扩缩容：当并发请求激增时，将服务副本从 1 个扩展到多个，通过负载均衡将海量请求分配到多个副本上，避免性能急剧恶化；当请求高峰期过后，再收缩副本数量，释放资源。

### 微服务：具有独立业务价值的单元

微服务是围绕业务功能分解为小型的、松耦合的各种服务，由独立团队开发和管理。每个服务专注于一个特定的任务，由一个小团队负责开发和运营。每个服务被视为一个独立的应用，有独立的团队、测试、开发、数据和部署。服务在独立进程中运行，相互之间通过同步或异步消息的 API 进行通信。

在传统单体应用处理高并发时，通常的做法是将整个应用完整地复制到多台服务器上，每台服务器都部署一份完整的功能模块。虽然技术上可行，但每个完整实例都占用大量资源，成本收益比不佳。微服务架构则按需伸缩：只有请求量大的服务需要进行扩容，流量小的服务保持原样即可。例如在一个包含购物车、订单、库存、物流等服务的电商系统中，秒杀场景下可能是订单和库存服务压力最大，只需要对这两个服务进行多副本扩容，而购物车或促销服务不需要额外资源。伸缩策略由 K8s 平台根据预设规则自动执行。

微服务架构的显著优势包括：**敏捷性**——每个微服务较小，适合采用敏捷开发方式；**故障隔离**——每个服务在独立沙箱中运行，一个服务的崩溃不会直接影响其他服务；**更好地利用云能力进行扩缩容**——可以按需对特定服务进行独立的水平扩展和收缩；**渐进式设计**——微服务可以被持续地拆分、迭代和优化设计；**持续创新**——通过不断演进服务边界和技术细节来支撑持续创新；**改善可观察性**——每个服务的运行状态和调用链路都可以被独立跟踪和观察。

但微服务架构也存在工程上的复杂性。一个前端请求可能涉及后端多个服务的连锁执行，需要协调这些调用的执行顺序和等待结果；数据库是采用单个共享数据库还是每个服务独立数据库，后者会带来数据同步和一致性问题。这些问题都需要在设计和运维层面精心处理。

### DevOps 与持续交付

DevOps 是 Development 和 Operations 的结合，强调开发和运维的融合，避免传统开发与运维之间的专业壁垒和冲突。DevOps 是一种敏捷思维、沟通文化，也是一种组织形式，为云原生提供持续交付能力打好文化基础。

**持续交付**要求不误时开发、不停机更新、小步快跑，反传统瀑布式开发模式。它要求开发版本和稳定版本并存，需要流程和工具支撑。传统瀑布开发流程中，只有前面每一步全部完成后才能进入下一步，一旦在最终测试或交付阶段发现问题，返工成本极高。敏捷开发通过将任务拆解为短周期迭代，一旦发现问题可以立即更正。开发者应避免将一个巨大版本一次性提交，而应小粒度地频繁 commit——每解决一个功能或修复一个 bug 都可以提交一次。这样一旦出现问题，可以快速定位到最近的迭代中哪些代码变更引发了问题。

### 传统应用与云原生应用的区别

云原生应用的核心变化之一是理念转变：**把系统看作产品，而非项目**。做项目和做产品有本质区别——项目的所有权在甲方，开发完成后移交给维护部门，开发团队就可以解散；而产品的所有权仍在开发公司。云原生应用要求开发团队对产品的整个生命周期负责，实践 **“谁建造，谁运维”** 的理念。亚马逊有一句名言 “You build it, you run it”，即“谁创造，谁运维”。开发团队要持续关注产品运行情况，与用户保持紧密联系，并承担售后支持。

在团队组织层面，传统模式是**烟囱式功能开发团队**——有专门的数据库团队、前端团队、中间件团队，分别完成后集成。云原生模式下，团队**围绕业务能力进行组织**——每个团队负责一个或多个服务的全生命周期。康威定律指出，组织的团队结构会逐渐与产品架构趋于一致：使用微服务架构的公司往往会建立与微服务对应的跨功能小团队。每个团队用合适的工具做合适的事，服务之间松耦合、独立部署，单一功能的改变只需重新构建和部署相应服务。

DevOps 工具链生态非常丰富。在版本控制与协作层面有 Git、GitHub、Gerrit；在构建与配置层面有 Maven、Gradle、Docker、Chef、Ansible；在代码扫描与测试层面有 SonarQube、JUnit、Cucumber、Selenium；在发布层面有 uDeploy、Azure DevOps；在部署层面有 Kubernetes、OpenShift、AWS 等。Jenkins 作为核心集成平台拥有超过 1000 个插件，可以将这些工具整合为自动化的端到端 CD 流水线。这也是企业实现降本增效的关键手段。

传统应用与云原生应用在工程方式上的差异体现在多个维度：传统方式是**手工驱动**——需求完成后大批量开发，集中测试，手工发布，事后运维，特点是反馈慢、环境差异大、变更风险集中；云原生方式是**小批量变更 → 自动验证 → 版本化制品 → 声明式发布 → 可观测反馈**，特点是持续学习、快速回滚、平台化治理。

在交付批量上，传统是大版本、周期较长，云原生是小批量、频繁验证。在环境管理上，传统是手工配置、容易漂移，云原生是声明式、版本化、可复现。在可靠性方面，传统强调避免变更、事后恢复，云原生则设计失败、自动恢复、快速回滚。在伸缩方式上，传统以垂直扩容为主，云原生按需组合水平与垂直扩缩容。在治理方式上，传统依赖工单与人工检查，云原生采用策略即代码、自动化证据与审计。

### 云原生应用十二要素

十二要素方法论源自 Heroku 的 SaaS 应用方法论，强调**可移植、可扩展和持续交付**。它是开发云原生应用时应考虑的一组最佳实践。

**第一，基准代码。** 每个云原生应用对应一个受版本控制的基准代码库，存放在版本控制系统中。一份基准代码可以多份部署，例如部署到开发、测试和生产环境；也可以做多副本部署。当多个应用共享代码时，应将其抽取为独立依赖，而不是让多个应用混合共用同一份代码。

**第二，依赖。** 应用应显式声明依赖关系。传统方式下，开发者克隆一个开源项目后，常常要反复安装各种缺失的依赖项，过程极其繁琐。云原生应用通过容器技术将依赖项打包在镜像内，部署时依赖已经就位，从而避免环境配置问题。

**第三，配置。** 配置是随着部署环境变化而变化的值，例如数据库地址、账号密码、密钥等。配置应与代码严格分离，不应硬编码在应用代码中。同一套代码通过不同的外部配置可以在不同环境中运行。在 K8s 中，ConfigMap 和 Secret 组件专门用于管理配置和敏感信息。

**第四，后端服务。** 后端服务指应用需要通过网络调用的各种支撑性服务，如数据库、缓存、消息队列、对象存储、外部 API 等。在云原生中，后端服务被视为可替换的资源，通过配置系统和外部访问来减少耦合。

**第五，构建、发布与运行。** 构建阶段是将源代码转变成不可变的、可版本化的制品的过程。发布阶段将构建制品与部署配置组合，形成唯一可追踪的发布版本。运行阶段是在目标环境中执行该发布。运行过程中禁止直接修改运行实例，任何变更都必须通过新的构建和发布流程来进行——这正是不可变基础设施的核心原则。

**第六，进程。** 应用以一个或多个无共享状态的进程运行。不同进程类型可以承担不同的工作。需要持久化的数据应写入数据库、对象存储或其他后端服务，而不应依赖单个实例的本地磁盘，以避免进程重建后数据丢失。

**第七，端口绑定。** 应用通过 IP 加端口的方式暴露服务，应用启动后监听指定端口的请求。在云原生环境中，域名请求通过 API 网关、负载均衡器或服务网格被路由到绑定端口的进程上。

**第八，并发。** 应用通过增加进程组的方式来应对并发请求。当负载增加时，可以水平扩展，创建多个进程实例来分摊请求；当负载下降时，减少进程实例数。

**第九，可处置性。** 进程应能够快速启动和优雅终止，正确响应平台发送的终止信号。在停止时应停止接收新请求，完成或安全转移在途任务，设置合理的超时后退出。这就需要容器环境提供就绪探针和存活探针等生命周期管理机制，来验证容器是否健康并妥善处理终止过程。

**第十，开发/生产等价。** 开发环境与线上环境应尽可能保持一致，减少环境差异。应用依赖的基础环境、后端服务版本、打包方式在开发、预发布和生产环境中都应一致。这与第二要素——依赖显式声明——密切相关。容器技术使得这种环境一致性更容易实现。

**第十一，日志。** 日志记录时间、日期、操作者和动作的相关信息。在微服务架构下，日志呈现为按时间顺序产生的事件流。日志应结构化、关联上下文，并避免泄露敏感信息。微服务应用往往有多个进程同时产生日志，如何合并和分析这些日志是后期可观测性阶段要解决的问题。

**第十二，管理进程。** 管理进程是指一次性运行、执行完后即终止的管理任务，如数据库迁移、批量数据处理等。管理进程应与常规业务进程分离，并与应用进程使用相同的代码基础和运行环境。

### 云原生技术体系的整体视角

云原生本质上是一种理念、一套技术体系、一种方法论和一种最佳实践的综合。从设计、开发、封装、编排到治理的各个环节都有相应的技术支撑：设计层面使用领域驱动设计（DDD）；开发采用敏捷方法；封装使用容器；资源编排使用 Kubernetes；功能编排使用微服务架构及 Spring Cloud、Service Mesh 等；维护依靠可观测性；治理针对大规模微服务的复杂性进行管理。

云原生平台在基础设施层面提供横切能力，包括可观测性、服务水平目标（SLO）管理、成本治理（FinOps）等。在运行平台层面，涵盖容器、服务网格、编排、网络和存储。在交互层面，涉及版本控制、CI/CD、基础设施即代码（IaC）和 GitOps。在架构层面，主要围绕**模糊边界**（服务模块如何划分）、**API 与事件**（模块间同步或异步通信）、**状态一致性**（各模块数据如何管理）以及**韧性模式**（应用在执行过程中如何感知故障并继续工作）展开。

云原生技术的最终目标是：**更快的反馈、可靠的服务、安全的合规，以及成本与效率的优化**。

### 课程实践项目概述

本课程实践项目是一个场地预约管理系统。基本业务围绕场地和预约两个核心概念展开：后台维护可用场地数据表，用户通过前端进行场地预约，系统判断预约是否存在冲突，并返回预约结果。这是一个典型的 MIS 系统场景。

项目实施分为三个阶段。**阶段一**：完成前后端系统开发与 Docker 容器化。任务包括最小业务的设计、后端 API 开发、简单前端实现、数据持久化、编写 Dockerfile，以及使用 Docker Compose 部署完整系统并进行运行验证。**阶段二**：Kubernetes 编排。增加异步报告任务模块，独立开发 worker 服务，编写 K8s 部署资源文件，实现多副本部署、滚动更新与回滚。**阶段三**：可观测性与故障诊断。为 API 增加指标采集（包括 Prometheus 指标收集、Grafana 可视化展示）、日志跟踪与收集、链路追踪（可选用 SkyWalking 等工具，以及 ELK 日志技术栈）。课程旨在让同学们将课堂所学工具实际应用一遍，避免“纸上谈兵”——至少能够真实地使用 Docker、Kubernetes、Prometheus、Grafana 以及日志采集与链路追踪的相关工具，积累实际的工程经验。
