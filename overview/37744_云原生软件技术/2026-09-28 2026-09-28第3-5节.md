### 课程背景：从 AI 应用到基础设施

课程开始前，老师从近期 AI 领域的快速变化切入，强调了本课程关注的不是 AI 模型本身，而是支撑这些模型的**基础设施层（Infrastructure，简称 Infra）**。当前大模型、智能体（Agent）等应用发展迅速，用户在使用 ChatGPT、豆包等产品时感受到的是流畅的交互体验，但其背后依赖的是大规模的服务器集群，其中包括大量 CPU 和 GPU 资源。如何合理管理这些异构资源、按需动态分配给用户，正是云原生软件技术所关注的核心问题。

与此前所学的虚拟化技术相比，**虚拟化**的核心目标是资源隔离：将一台完整机器的底座切分为多个相互隔离的单元，让每个用户感觉独占整台机器。而**云原生**则更接近一种商业模式，强调资源的按需共享与按需付费。IaaS 层提供自动化的虚拟化资源租赁，PaaS 层提供开发部署平台（如 CI/CD）并收费，SaaS 层则以订阅制方式提供应用软件。本课程前半部分聚焦于如何更好地管理和封装资源，具体就包括本次课的容器化技术与 Docker，后续还将涉及 Kubernetes 对多容器的编排管理。

### 传统应用部署的困难

#### 从传统 Web 应用部署说起

在早期的 Web 应用开发中，由于缺少 Spring Boot 等现代框架，开发者常用 Java 编写后台工程（如 SSH 框架），编译后将 class 文件或整个项目文件夹部署到 Tomcat 等 Web 应用服务器的特定目录下（如 `webapps` 目录）。部署形式包括直接拷贝文件夹，或将应用打包为 WAR 包（本质上是一个 zip 压缩文件，只是使用了专门的 `.war` 后缀名），Tomcat 启动时会自动解压该包。用户通过 `http://域名:8080/应用名` 访问，默认入口页通常是 `index.jsp` 或 `index.html`。

#### 部署中常见的三类问题

当开发者将本地测试通过的应用部署到用户现场时，会面临多种问题。

**环境变量与配置参数不一致**：应用启动依赖大量的环境变量和配置参数。如果这些参数在目标环境中没有正确设置，应用可能根本无法启动，或启动后功能异常。

**第三方依赖缺失**：现代开发大量使用第三方库和框架。开发者本地环境中安装了完整的依赖，但交付到用户环境时往往只携带了应用本身，目标机器上可能缺少所需的依赖包，导致运行失败。类似地，从 GitHub 克隆开源项目到本地后，按照文档执行却总是报错，往往也是因为仓库只上传了应用代码，而没有附带依赖配置，需要根据报错信息逐一手动安装依赖。过去开发者遇到此类问题通常需要到 Stack Overflow 上检索答案，现在则可以直接询问大模型，效率大幅提升。

**开发环境与生产环境的根本差异**：在业界术语中，**开发环境**指开发者本地的编码测试环境，**生产环境**（也称用户环境或运行环境）指应用真正面向最终用户运行的环境。两者在服务器配置、操作系统版本、基础中间件和依赖库等方面都可能存在显著差异。因此才有了那句经典抱怨：“**It works on my machine**”——在开发机器上运行正常，部署到用户环境却出问题。

### 为什么需要容器

#### 传统单体应用的局限

传统应用多为**单体应用**：多个功能模块作为一个整体进行构建和部署，模块之间通过进程内调用交互，整个应用是一个独立进程。这种架构的缺点是发布周期长、变更成本高。过去企业级应用可能几年才更新一次，但现在为了吸引用户，移动应用可能几周发一次版本，在线 Web 应用甚至以小时为单位滚动上线。单体应用已难以适应快速迭代的需求。

#### 现代应用的趋势与挑战

现代应用呈现**模块化、服务化或事件驱动**的趋势，要求快速迭代、频繁交付，并且工作负载需要**动态部署和伸缩**，以应对高并发流量场景。当请求量激增时，需要快速增加容器实例来分担负载。

这带来两个主要挑战：其一，技术栈和运行依赖更加多样，基础环境愈发复杂，需要快速创建一致的运行环境；其二，应用组件数量显著增多，例如淘宝、京东等大型系统的背后可能包含数千个微服务，每个服务以容器形式封装部署，因此需要以自动化方式管理复杂系统。

### 容器的定义

**容器**是将应用及其**用户空间依赖**（如第三方库）一起打包为可分发**镜像（Image）**，并以**相互隔离的进程形式**运行的机制。每个容器是一个进程组，不同容器之间相互隔离。需要注意的是，镜像打包时**不包含宿主机操作系统的内核**（OS Kernel），这一点在后续与虚拟机对比时尤为关键。

容器为应用提供标准化的构建、分发和运行单元。使用者通过镜像、端口和配置等**契约**来使用应用，而不必了解镜像内部的全部实现细节。这与面向对象中的**信息隐藏**和**关注点分离**原则一致。容器工具和运行时支持一致的操作，包括构建、分发、启动、停止和删除。

**镜像与容器的关系**可以类比为面向对象中的**类和实例**：镜像是打包好的模板，可以被多次实例化为多个独立运行的容器，形成一对多的关系。

#### 容器的标准化类比：集装箱

容器的思想可以类比物流行业的**集装箱**。集装箱是标准化的运输单元，可以稳固堆叠、方便吊装，在不同运输工具（卡车、货轮）之间高效转运。软件行业希望将应用也封装为类似集装箱的标准化单元，只要底层运行环境支持该标准，应用就能在不同机器上以相同方式运行。Docker 的标志正是一只驮着集装箱的鲸鱼，形象地体现了这一理念。

### 容器技术的优点

#### 轻量化

容器与虚拟机相比，最显著的优势是轻量。虚拟机无论是 Type 1 裸金属架构还是 Type 2 宿主架构，每个虚拟机内部都包含一个完整的 **Guest OS**，体量通常以 GB 计。而容器**共享宿主机内核**，镜像中只包含应用本身及其依赖，不包含操作系统内核，因此镜像大小通常以 MB 计（几百 MB 较为常见），创建和启动速度也远快于虚拟机。

#### 细粒度资源控制

容器通过 **cgroup** 等机制设置 CPU、内存和 I/O 的权重或上限，约束资源使用。给容器设定资源上限的意义在于**避免资源竞争**：防止一个应用占用过多资源，导致其他应用无资源可用。但 cgroup 并不能完全消除所有资源竞争。

#### 较低的虚拟化开销

容器也可以视为一种虚拟化技术，但其虚拟化方式与虚拟机不同。容器**不需要模拟完整硬件和 Guest OS**，不需要虚拟化底层 CPU 和内存，因此开销远低于虚拟机。

#### 环境一致性

容器镜像包含应用及其用户空间依赖，使得开发、测试和生产环境保持一致。开发者只需关注功能逻辑，不必担心部署到用户环境后因环境差异而出问题。不过可移植性仍受**操作系统内核、CPU 架构、设备和运行时配置**等条件约束。例如，容器天然最适宜运行在 Linux 系统上；在 Windows 上运行容器通常需要借助 WSL2 在 Windows 内运行一个 Linux 虚拟机，再将容器环境部署于该虚拟机中。此外，一些带有 GUI 界面的应用在 Linux 上容器化运行正常，但在 Windows 上可能无法正常显示界面。

#### 管理便捷性

以镜像和容器为标准单元，使应用的**版本管理、部署、迁移、扩缩容和回滚**更加一致。镜像可以添加 label 标签来标注版本号（如 v1、v2、v3），便于迭代管理。

### 容器技术的缺点

容器的主要局限在于**隔离边界弱于虚拟机**。虚拟机通过 Hypervisor 将资源完全隔离，每个虚拟机内有独立的 Guest OS，一个虚拟机中的应用基本不可能看到另一个虚拟机内部的情况，属于**强隔离**。而同一宿主机上的 Linux 容器**共享宿主机内核**，每个容器只是不同的进程组，逻辑上隔离但共享内核。如果内核存在漏洞或配置不当，可能扩大安全影响范围。

为降低风险，可以结合**最小权限、非 root 运行、用户命名空间、能力控制、seccomp 和强制访问控制**等安全机制。这些属于更细粒度的运维安全话题，本课程不做深入展开，但需要了解容器隔离是**逻辑隔离**而非硬隔离。

### 容器与虚拟机的对比

| 特性 | 容器 | 虚拟机 |
|------|------|--------|
| 启动速度 | 秒级 | 分钟级 |
| 硬盘使用 | 一般为 MB | 一般为 GB |
| 性能 | 接近原生 | 弱于原生 |
| 单机支持量 | 上千个容器 | 一般几十个 |

从架构图来看，虚拟机方案在基础硬件之上运行 Hypervisor（VMM），其上为每个虚拟机分别安装独立的 Guest OS，再在其上运行二进制文件、库和应用。每个虚拟机都必须包含一个完整的 Guest OS，因此体量大、开销高。

容器方案则在基础硬件之上安装主机操作系统（如 Linux），再在其上安装容器运行环境（如 Docker）。每个容器内部**只包含应用及其二进制文件和依赖库**，不包含客户操作系统。所有容器共享宿主机内核，通过容器运行时统一管理，因此轻量且启动迅速。

### 容器的核心技术

容器背后的核心机制有三项：**Namespace**（命名空间）、**cgroup**（控制组）和 **rootfs**（根文件系统）。

#### Namespace：资源视图隔离

Namespace 是 Linux 内核提供的**资源视图隔离机制**，使一组进程只能看到分配给其命名空间的部分系统资源。不同的命名空间可以看到不同的计算、存储、网络等资源，形成一个逻辑隔离边界。它提供的是**隔离视图，而非完整的安全边界**。

Linux 提供了多种类型的 Namespace：

| Namespace 类型 | 系统调用参数 | 隔离内容 | 内核版本 |
|---------------|-------------|----------|---------|
| UTS | CLONE_NEWUTS | 主机名和域名 | 2.6.19 |
| IPC | CLONE_NEWIPC | 信号量、消息队列和共享内存 | 2.6.19 |
| PID | CLONE_NEWPID | 进程编号 | 2.6.24 |
| Network | CLONE_NEWNET | 网络设备、网络栈、端口等 | 2.6.29 |
| Mount | CLONE_NEWNS | 挂载点（文件系统） | 2.4.19 |
| User | CLONE_NEWUSER | 用户和用户组 | 3.8 |

UTS 命名空间隔离主机名和域名，使每个容器拥有独立标识；IPC 命名空间隔离进程间通信资源（信号量、消息队列、共享内存），确保容器间互不干扰；PID 命名空间隔离进程 ID 空间，容器内进程只能看到同一容器内的其他进程，防止进程 ID 冲突；Network 命名空间隔离网络资源，使容器拥有独立的网络接口、IP 地址、路由表和防火墙规则；Mount 命名空间隔离文件系统挂载点，使容器拥有自己的文件系统视图，可以映射到宿主机的不同目录实现持久化存储；User 命名空间隔离用户和用户组，使容器内部用户与宿主机和其他容器隔离。

可以通过 `clone()`、`unshare()` 和 `setns()` 等系统调用来创建或加入 Namespace。现代 Linux 还提供 cgroup 和 time 等额外的 Namespace 类型。

#### cgroup：资源使用限制

Namespace 隔离了进程看到哪些资源，但**不负责限制进程消耗多少资源**。如果没有资源控制，一个容器中的进程可能过度消耗 CPU、内存或 I/O，影响宿主机系统和其他容器的稳定性。

**cgroup（Control Groups）** 是 Linux 内核的一项功能，用于对一组进程进行**资源统计、优先级控制和限额管理**。它和 Namespace 共同构成容器的重要基础。cgroup 本身也不等同于安全隔离。

cgroup 的主要功能包括：

**资源限制**方面，CPU 限制可通过配额限制进程组在一个周期内可使用的 CPU 时间。例如将平均计算能力限制为约 0.5 个 CPU 核，意味着在一个调度周期内，该容器只能使用一个核心 50% 的计算时间切片。内存限制则是设置内存使用上限，超出后内核会尝试回收内存，并可能在对应 cgroup 中触发 **OOM（Out Of Memory）** 处理，终止一个或多个进程。磁盘 I/O 限制可对块设备设置 I/O 带宽或 **IOPS**（每秒输入/输出操作次数）上限，降低单个工作负载过度占用磁盘的影响。

**资源权重与保护**方面，CPU 权重决定资源竞争时权重较高的 cgroup 获得更多 CPU 时间，空闲时仍可使用未被占用的计算资源。内存保护方面，cgroup v2 可以配置内存保护和回收优先级：当系统内存不足、内核必须回收内存时，优先从没有保护或保护程度较低的 cgroup 中回收，尽量不回收受保护 cgroup 正在使用的内存。

**资源统计**方面，cgroup 记录 CPU 统计（进程组消耗的 CPU 时间、被限流时间）、内存统计（当前使用量、峰值、内存事件和不同类型内存的使用情况）、磁盘 I/O 统计（读写字节数、操作数），起到审计和持续监控的作用。

**资源隔离**方面，通过将 CPU 核心分配给不同容器、限制容器的内存使用、限制磁盘 I/O 速度等方式，确保各容器之间的资源相互隔离。

#### rootfs：根文件系统

**rootfs** 是容器进程看到的**根文件系统**，是容器运行环境的重要组成部分。它通常包含应用、系统工具和依赖库等用户空间文件；运行时配置、密钥和数据也可以通过挂载在启动时注入。rootfs **不包含操作系统内核**，同一宿主机上的 Linux 容器共享宿主机内核，但看到的是各自隔离的文件系统视图。

容器镜像提供**只读文件系统层**，启动容器时通常在其上增加一个**可写层（writable layer）**，并可挂载 **Volume** 或主机目录。从结构图来看，最底层是 `bootfs`（内核，不包含在容器内），其上依次是 `Base Image`（如 Debian 基础镜像）、`add emacs` 镜像层、`add Apache` 镜像层，最上方是容器的可写层。多个镜像和容器可以共享相同的只读层，从而节省空间。

### Docker 概述

需要明确：**Docker 是容器技术的一种实现工具，容器并不等同于 Docker**。容器是一种通用技术，而 Docker 是当前最主流、使用最广泛的容器工具。

#### Docker 的定义与起源

Docker 是一个面向开发者和系统管理员的开放平台，用于**构建、分发和运行分布式应用**。其核心组件包括 **Docker Engine**（一个轻量级、可移植的容器运行时和打包工具）和 **Docker Hub**（用于存储镜像的云仓库，类似于 GitHub）。

早期 Linux 容器技术已经提供了隔离能力，但 Docker 通过**镜像格式、分层构建、Registry 和一致的工具链**显著改善了开发和交付体验。Docker Engine 是开源容器引擎，由 dotCloud 公司于 2013 年开源。早期 Docker 使用 **LXC（Linux Containers）**，之后发展出 **libcontainer、runc 和 containerd** 等组件。dotCloud 当时采用“基础版开源、商业版收费”的策略：社区版（Community Edition）开源，吸引贡献者提升质量；商业版（Enterprise Edition）面向企业客户，核心价值在于提供 7×24 小时运维支持。

Docker 提供开发、构建、分发和运行容器化应用的工具与服务：能够把应用及其依赖构建为镜像，并通过容器运行；一台物理机或虚拟机上可以运行多个 Docker 容器。

#### 镜像分层与联合挂载

Docker 镜像由多个**只读层**和镜像配置组成，利用**联合挂载技术（Union Mount）**将多个文件系统层组合为统一视图。Docker 在 Linux 上通常通过 **overlay2** 等存储驱动实现镜像分层和容器可写层。多个镜像和容器可以共享相同的只读层，容器启动时增加一个容器专用的可写层。对文件的修改写入可写层，而**持久业务数据应使用 Volume 或其他外部存储**，因为可写层的生命周期与容器绑定，容器删除后数据即丢失。

### Docker 架构

#### Client-Server 总体架构

Docker 采用典型的客户端-服务端架构。**Docker Client** 通过 Docker API 向 **Docker Daemon** 发送请求，客户端可以是命令行工具或可视化平台工具。**Docker Host** 是运行 Docker Engine 的主机，其中 **Docker Daemon** 负责管理镜像、容器、网络和 Volume。**Registry**（如 Docker Hub）是镜像仓库，负责存储和分发镜像。Images 和 Containers 的关系如前所述：镜像类似于类，容器是镜像的实例。

典型工作流是：客户端通过 `docker pull` 从 Registry 将镜像拉取到本地环境，再通过 `docker run` 将镜像实例化为多个运行中的容器。如果执行 `docker run` 时镜像不在本地，Docker 会先自动从 Registry 拉取，再执行运行操作。

#### 早期内部机制

Docker 早期架构中，Docker Daemon 内部包含 Docker Server（提供 API 入口）和 Engine。Engine 中使用 Job、Graph 等内部抽象，`graphdriver` 负责镜像的寻址存储和构建，`networkdriver` 管理容器网络，`execdriver` 限制容器运行资源或执行用户指令（该组件现已被移除）。底层的 `libcontainer` 库与 Linux 内核交互，后来演化为 **runc** 的重要基础。现代 Docker 使用内容寻址镜像、存储驱动，并通过 **BuildKit** 执行镜像构建；容器生命周期管理委托给 **containerd**。当前常见调用链为 **Docker Engine → containerd → containerd-shim → runc**。

#### 现代容器运行时架构

在现代架构中，Docker Client 发出请求后，经过 **Docker Engine** 转发给 **containerd**。containerd 负责**镜像分发与存储、快照、容器生命周期和任务监控**等核心能力，并可通过插件扩展。containerd 准备镜像快照和 **OCI（Open Container Initiative）** 配置后，为每个容器创建 **shim** 进程。shim 调用 **runc** 来创建并启动容器进程；runc 完成任务后退出，由 **shim** 继续监控容器进程。这样设计的目的是让上层引擎与具体运行时解耦，runc 作为一次性容器创建工具无需常驻运行。

**runc** 是 OCI 运行时规范的参考实现之一，源自 Docker 的 libcontainer，可以独立于 Docker Engine 使用。它利用 Namespace、cgroup、rootfs 和安全机制建立容器运行环境，创建容器进程后通常退出。**containerd-shim** 则是专门管理单个容器进程的常驻组件，在 runc 退出后持续监控容器的生命周期。

### Repository 与 Registry

**Repository** 保存同名镜像的不同标签或版本。镜像名称通常带有冒号和标签（tag）来标识版本，若不加标签则默认使用 `latest`（最新版本）。**Registry** 提供镜像存储与分发服务，可以托管多个 Repository；Docker Hub 是公共 Registry 之一。Registry 和 Repository 都可以设为公开或私有，并实施访问控制。

使用 `docker push` 上传镜像到 Registry，使用 `docker pull` 下载镜像。生产部署建议使用**固定版本标签或镜像摘要**，而非 `latest`，以避免每次拉取到不同版本镜像造成不确定性和困扰。国内由于网络原因有一些 Docker Hub 的镜像站（mirror），保持与官方仓库的同步。

### Dockerfile

**Dockerfile** 是用于构建容器镜像的**文本文件**，按顺序描述基础镜像、文件复制、构建命令、元数据和默认启动方式。`docker build` 读取 Dockerfile 并生成分层镜像，后再通过 `docker run` 将镜像实例化为容器。

#### 常用模板指令

- **FROM**：指定构建阶段的基础镜像，一般是第一条指令。
- **LABEL**：设置镜像元数据。
- **ENV**：设置镜像中的环境变量，如 `ENV APP_ENV=production`。
- **RUN**：在构建阶段执行命令并生成镜像层，如 `RUN apt-get update && apt-get install -y curl`。
- **COPY**：从构建上下文复制文件或目录到镜像。
- **ADD**：与 COPY 类似，但额外支持本地 tar 解包等能力；普通复制优先使用 COPY。
- **EXPOSE**：声明监听端口，但不自动发布；运行时使用 `-p` 或 `-P` 发布。
- **WORKDIR**：设置后续指令及容器的默认工作目录。
- **VOLUME**：声明外部存储挂载点；具体存储在运行或编排时配置。
- **CMD**：设置默认命令或参数。此外还有 **ENTRYPOINT** 指令（PPT 中未列出），其优先级高于 CMD：如果配置了 ENTRYPOINT，容器启动时会执行 ENTRYPOINT 所指定的命令，CMD 中配置的内容则作为参数附加到 ENTRYPOINT 命令之后。

#### Dockerfile 示例

以下是一个将 WAR 包部署到 Tomcat 的典型 Dockerfile：

```dockerfile
FROM tomcat:10.1-jre17-temurin
# 使用Tomcat 10.1与Java 17运行时镜像

WORKDIR /usr/local/tomcat
# 设置后续指令和容器的默认工作目录

COPY test.war webapps/test.war
# 将WAR包复制到Tomcat部署目录

EXPOSE 8080
# 声明应用监听8080端口；运行时仍需-p发布

CMD ["catalina.sh", "run"]
# 以前台方式启动Tomcat，使其成为容器主进程
```

该示例首先基于 `tomcat:10.1-jre17-temurin` 基础镜像（已包含 Tomcat 10.1 和 Java 17 运行环境），设置工作目录为 `/usr/local/tomcat`，然后通过 COPY 指令将本地的 `test.war` 复制到容器内的 `webapps` 部署目录。`EXPOSE 8080` 只是声明容器将监听 8080 端口，真正对外发布仍需在执行 `docker run` 时使用 `-p` 参数。最后通过 `CMD` 以前台方式启动 Tomcat，使其成为容器主进程。若要将当前目录下所有文件复制到镜像中，COPY 的源路径可以使用 `.`（点号）。

### Docker 基本命令

#### 管理镜像

**下载镜像**：从 Registry 拉取指定标签的镜像。

```bash
docker pull image_name:tag
```

如果不指定 tag，则默认拉取 `latest` 版本。

**列出本地镜像**：

```bash
docker image ls
```

**构建镜像**：使用当前目录中的 Dockerfile 构建镜像。

```bash
docker build -t team/image:tag .
```

其中 `-t` 指定镜像名称和标签，最后的 `.` 表示使用当前目录作为构建上下文，不可省略。

**推送镜像**：将已正确命名并登录授权的镜像推送到 Registry。

```bash
docker push team/image:tag
```

#### 运行和管理容器

**创建临时容器并运行命令**：

```bash
docker run --rm image_name:tag echo "hello world"
```

其中 `--rm` 表示容器结束后自动删除，`echo "hello world"` 是覆盖 CMD 的执行命令。

**列出当前正在运行的容器**：

```bash
docker container ls
```

`docker run` 中包含许多重要参数。`-p` 用于发布容器端口，建立宿主机真实端口与容器端口的映射，使外部流量能路由到容器；`-d` 用于后台运行；`-v` 用于将容器内部的文件目录映射到宿主机外部挂载点，实现持久化存储。此外还有交互模式参数等，可通过 `docker help` 查看各指令的具体参数说明。
