### 直接使用物理设备的不足

在引入虚拟化概念之前，老师首先从操作系统资源管理的角度出发，指出操作系统南向管理异构资源，北向支撑应用执行。在一台物理服务器中，无论计算资源、存储资源还是网络资源，都集中在一台设备之内。计算资源主要包括服务器 CPU 和内存容量，当前 GPU 同样可以作为虚拟化对象；存储资源主要指服务器磁盘空间；网络资源则包括服务器网卡、网络类型、路由器和网关等。老师在此特别指出，现实世界中的网络类型远比课堂上常见的 TCP/IP、HTTP 更加复杂。例如船舶行业强调多网融合，近岸时可使用 5G 网络，远洋时则切换为卫星网络；军事作战环境中的网络条件则更为受限，存在所谓的 DDIL 环境，即带宽受限、抖动、间歇性连接和低带宽等特征。这些不同行业对网络资源的管理需求，也是虚拟化和云计算需要面对的复杂问题。

传统的应用部署方式，是直接在一台物理服务器上安装 Web 应用服务器（如 Tomcat），再在其上部署 Web 应用，或者使用 Spring Boot 等方式将应用直接部署在单一服务器上。随着技术发展和对资源利用率要求的提高，这种直接使用物理设备的方式暴露出多方面的不足。

**缺乏时间灵活性**是第一个显著问题。当应用面临高并发访问时，例如学校选课系统在开学阶段被大量用户同时访问，单台服务器的计算资源会被迅速耗尽。此时需要扩容，但传统扩容往往涉及硬件采购、合同签订、设备到货、安装部署等一系列流程，所需时间较长，无法及时应对突发的高并发请求。

**缺乏空间灵活性**则表现为资源浪费。很多应用的实际规模很小，但为了运行该应用，企业可能购置了一台高性能服务器，花费数万元甚至更多。然而该服务器的 CPU 资源利用率长期仅在 5%～10% 左右，大部分算力处于闲置状态，造成严重的资金和能源浪费。

**缺乏操作灵活性**体现在设备上架、安装和配置都需要大量人工操作。传统的命令行配置方式，尤其是网络设备配置，需要针对多台不同设备逐一手动操作，缺少统一的控制面来进行集中管理和自动化配置。

除了灵活性缺失，直接使用物理设备还存在**隔离性差**的问题。为了提高资源利用率，通常会将多个服务部署在同一台物理服务器上。由于这些服务共享同一操作系统内核，服务之间可能发生相互干扰，甚至通过网络攻击手段从一个应用获取其他应用的数据，造成安全隐患。特别是在处理敏感或隐私数据时，隔离性的不足可能导致严重的数据泄露问题。

**不可复制**是另一个重要缺陷。当物理设备上的应用需要扩展时，只能先增加物理设备，再重新执行一遍资源配置、操作系统安装、依赖包配置、网络设置和应用发布等完整流程。这种复制过程耗时耗力，且难以保证每次复制的配置一致性。老师以 GitHub 上的开源项目为例指出，很多项目克隆到本地后直接运行往往会出现大量依赖包缺失的错误，需要逐一解决依赖问题才能成功部署，这正是物理环境不可复制性的直观体现。

### 虚拟化的原理与广义虚拟化

针对上述物理设备使用方式的不足，虚拟化思想被引入。虚拟化的历史可以追溯到 20 世纪 60 年代的分时技术。分时操作系统的核心思想是让多个任务共享 CPU，通过时间片轮转调度，使每个任务在逻辑上感觉自己独占 CPU。1964 年开始的 IBM CP-40 项目通常被视为早期完整虚拟化的重要实践，该项目在 IBM 360 机器上实现了分时虚拟化。

虚拟化的本质是在物理资源与上层软件之间引入抽象层，向上提供与底层实现相对独立的逻辑资源。抽象这一概念在计算机学科中极其重要——它屏蔽底层差异，提取共性特征。在操作系统层面，虚拟化将底层的 CPU、内存、磁盘和网络等硬件资源抽象为逻辑资源，分配给多个操作系统。每个操作系统从自身角度看来，都像是独占了一整套完整的硬件资源，而实际上它们共享的是同一台物理机的资源。

从更广泛的角度来看，虚拟化包含多个层面。**硬件虚拟化**是最直观的形式，通过 Hypervisor 向上层提供虚拟硬件，使多个 Guest OS 能够在同一物理主机上运行。**内存虚拟化**通过虚拟地址空间等机制抽象物理内存，为进程提供相对独立、连续的地址空间。需要注意的是，内存虚拟化与 Windows 系统中的"虚拟内存"概念不同——后者指的是当物理内存不足时，将硬盘空间用作内存扩展，通过 swap 交换机制将数据在内存和硬盘之间搬运，以突破内存容量限制。**操作系统层虚拟化**则是直接模拟出完整的操作系统环境，实现对应用的独立封装和隔离。**应用虚拟化**在应用层或函数层之上建立抽象层，提供逻辑隔离功能，允许一个应用同时支撑多个用户应用，这就是所谓的多租户模式。例如很多在线应用系统，所有用户访问的是同一套后台应用，但通过数据隔离和逻辑隔离，每个用户感觉像是独占了该应用。

老师在此特别指出，虚拟化的核心内涵是：虽然底层硬件基础设施、操作系统或软件只有一套，但通过虚拟化可以产生多个"分身"，共享给不同用户使用，令每个用户都感觉自己拥有独立的一份资源。

### 服务器虚拟化

服务器虚拟化是将虚拟化技术应用于服务器场景的具体形式。其定义来自美国国家标准与技术研究院（NIST SP 800-125）：虚拟化为应用程序的运行提供包含软硬件资源的仿真环境，这一组仿真环境被称为虚拟机。

服务器虚拟化通过在一台物理主机上运行多台虚拟机，使每台虚拟机看到相对独立的虚拟硬件，包括 vCPU、内存、磁盘和网卡等，并运行独立的客户操作系统（Guest OS）及其应用。用户可以为虚拟机选择不同的计算、内存和存储规格，也可以挂载不同存储并配置到不同虚拟网络中。老师以阿里云为例说明：用户在阿里云控制台中可以租用虚拟机，自由选择 CPU 核数、内存大小、硬盘空间和网络带宽；这些虚拟机背后是阿里云分布在华东、华北等区域的大型服务器集群，用户通过 SSH 远程登录分配好的服务器即可使用。

服务器虚拟化的实现依赖于 Hypervisor 或虚拟机监视器（VMM）。这两个术语在大多数情况下可以视为同义词：VMM 更多出现在学术论文中，Hypervisor 则是工业界的常用称呼。Hypervisor 通过资源划分、分时调度和设备虚拟化等机制，将服务器物理资源抽象为逻辑资源，分配给各个虚拟机。多个 vCPU 在逻辑上相互隔离，但仍然共享底层物理 CPU，因此可能发生资源竞争。现代虚拟化技术已经能够实现相当严格的资源隔离，但并非绝对等同于物理隔离。

虚拟机具有四个基本特征。**分区**指一台物理机上可以同时运行多个虚拟机，每个虚拟机占据不同的资源分区。**隔离**指同一物理机上的多个虚拟机之间逻辑资源相互隔离，一个虚拟机无法查看另一个虚拟机的内部数据。**封装**指虚拟机的完整执行环境（包括硬件、操作系统和应用）可以被封装在独立的文件或镜像中。**独立**指封装好的虚拟机镜像可以在不同的服务器上部署运行，无须修改即可迁移，前提是目标服务器上安装了相应的虚拟化产品。

常见的虚拟化技术与工具包括 VMware、Xen Project、KVM、QEMU、VirtualBox 和 libvirt 等。其中 VMware 是著名的商业化虚拟化公司；Xen Project 是较早期的开源虚拟化项目；KVM 和 QEMU 在编译和系统研究中经常使用；VirtualBox 和 VMware Workstation 是桌面端常用的虚拟化工具。

### 虚拟化实现机制

虚拟化实现机制描述的是 Guest OS 与 Hypervisor 之间的交互方式，主要分为全虚拟化、半虚拟化和硬件辅助虚拟化三类。硬件辅助虚拟化可以与全虚拟化或半虚拟化结合使用，并非与前两者完全互斥的独立类别。

**全虚拟化**的特征是 Guest OS 无须任何修改即可在虚拟化环境中运行。Hypervisor 向 Guest OS 提供完整的虚拟硬件环境，使 Guest OS 感觉自己运行在一台真实的物理主机上。VMware Workstation 等产品属于全虚拟化类型。早期的纯软件实现方式性能开销较大，因为应用需要先调用 Guest OS，再经过 Hypervisor 间接访问物理硬件，调用链路较长。现代实现通常结合硬件辅助虚拟化和半虚拟化 I/O 驱动（如 virtio），性能开销已显著降低。

**半虚拟化**是一种 Guest OS 或设备驱动与 Hypervisor 协作的机制。与全虚拟化不同，半虚拟化中的 Guest OS 需要知道底层硬件是虚拟化环境，其中部分组件（特别是设备驱动）需要与 Hypervisor 直接交互和协作。半虚拟化通过 Hypercall 或半虚拟化驱动减少部分虚拟化开销。典型早期实现是 Xen PV。传统半虚拟化需要修改 Guest OS，兼容性因此受限——经过修改的操作系统无法直接运行在其他虚拟化产品上。但现代虚拟机中也常使用 virtio 等半虚拟化 I/O 驱动，在保持兼容性的同时获得性能收益。

**硬件辅助虚拟化**利用处理器提供的虚拟化扩展，如 Intel VT-x 和 AMD-V，帮助 Hypervisor 高效、安全地运行虚拟机。这些处理器的虚拟化扩展可以减少软件模拟和特权指令处理的开销。现代全虚拟化通常都会结合硬件辅助机制来提升性能。

### 虚拟化架构：裸金属架构与宿主模式架构

虚拟化产品在架构上分为两种类型：裸金属架构（Type 1）和宿主模式架构（Type 2）。

**裸金属架构（Type 1）**中，Hypervisor 直接运行在物理硬件之上，负责管理 CPU、内存和 I/O 等底层资源。它不依赖传统的宿主操作系统。部分实现包含管理域或管理操作系统，但其角色不同于 Type 2 架构中的 Host OS。在裸金属架构下，各虚拟机运行自己的 Guest OS，并通过 Hypervisor 共享和隔离底层硬件资源。VMware vSphere 和 KVM 等属于裸金属架构。由于应用通过 Guest OS 直接经由 Hypervisor 访问硬件，执行效率相对较高。老师以智能网联汽车为例说明：车辆内部包含多个计算域，如车控域、自驾域和智能座舱域。车控域对实时性和安全性要求极高，通常采用黑莓公司的高可靠实时操作系统；自驾域负责自动驾驶决策，如特斯拉的 FSD 端到端大模型；智能座舱域处理娱乐和交互功能。这些不同域的计算通常通过芯片级虚拟化（SoC 上的虚拟化）进行隔离，多采用裸金属架构来满足高实时性要求。

**宿主模式架构（Type 2）**中，虚拟机监视器被安装和运行在常规操作系统之上，依赖宿主操作系统对硬件设备的支持和对物理资源的管理。典型的宿主模式虚拟化产品包括 VirtualBox 和 VMware Workstation 等。在这种架构下，虚拟机中的应用需要先访问 Guest OS，再经过宿主操作系统中的 VMM，最后通过 Host OS 访问硬件，调用链路较长。但虚拟机监视器依然可以充分利用宿主操作系统对硬件设备的支持以及内存管理、进程调度等服务，因此个人桌面使用场景下通常不会有明显问题。例如在 macOS 上安装 Parallels Desktop 或 VirtualBox 来运行 Windows 虚拟机，或是在鸿蒙 PC 操作系统上通过虚拟机运行 Windows 应用，都属于宿主模式虚拟化的典型应用场景。

### 虚拟化的不足与云计算的引入

虚拟化能够有效提高硬件资源利用率，并为工作负载提供逻辑隔离。然而，仅有单机 Hypervisor 并不等同于完整的云管理平台。如果缺少资源池、自助服务和统一自动化管理，虚拟化仍存在多方面的不足。

**资源获取时间较长**。只有 Hypervisor 而没有云管理平台时，虚拟机的申请、审批、放置和配置仍可能依赖人工流程。老师以学院机房为例：申请课程教学用的虚拟机需要填写表单、提交审批、由管理员分配资源，虽然是分钟级的获取过程，比采购物理设备快得多，但仍涉及人工流程。随着环境规模扩大，人工操作会增加交付时间和配置不一致风险。相比之下，容器技术可以实现秒级启动，而在 AI Agent 推理等对实时性要求更高的场景中，即使是秒级启动也可能不够，人们开始追求毫秒级的计算资源拉起能力。

**资源粒度与容量调节不够灵活**。单机虚拟化不能独立提供跨集群的资源池化和弹性调度。如果业务负载需要快速增加或释放资源，仅靠单机虚拟化难以实现，还需要集群管理、容量规划和自动化调度能力的支撑。

**资源操作与治理自动化不足**。仅使用 Hypervisor 时，通常缺少统一的资源目录、租户管理、配额、计量和策略控制。而云管理平台可以通过 API、声明式配置和自动化流程，使资源申请、变更、回收和审计更加一致和自动化。

针对这些问题，云计算进一步提出了资源自助获取、资源池化、快速供应、弹性调节和可度量等目标。云管理平台通过控制平面和调度器统一管理计算、存储和网络资源，并根据容量、策略和租户需求选择合适的资源。这种能力通常被称为资源池化或云化管理。需要注意的是，虚拟化是云计算常用的支撑技术，但并非云计算的完整定义，也不是唯一实现方式——云计算的内涵更广，底层也不一定完全依赖虚拟化。

### 云计算的特点与本质

根据 NIST SP 800-145 的定义，云计算是一种通过网络按需访问共享、可配置计算资源池的模式，资源能够快速供应和释放，并尽量减少人工管理和服务提供商交互。云计算具有五个核心特点。

**按需自助服务**指用户无须与服务提供商人员直接交互，即可按需自动获取计算资源。用户通过控制面或 dashboard 即可自助申请和使用资源。

**广泛网络接入（访问无边界）**指用户可以通过标准机制，经网络从不同类型的客户端访问云服务。无论是 PC、手机、已部署的应用还是 IoT 设备，都可以通过网络访问云资源，但需要经过权限控制和身份认证等安全机制。

**资源池化**指服务提供商将计算资源组织成共享资源池，以多租户方式按需动态分配和释放资源。老师以共享单车为例做了类比：用户并不拥有单车的所有权，但可以付费获得一段时间的使用权；每次出行使用的车辆不必是同一辆，有空闲资源即可扫码使用。这种共享模式本质上与云计算的资源池化逻辑相通。

**快速弹性（极速伸缩）**指资源可以快速、弹性地供应和释放。对用户而言通常表现为可按需获取、近乎不受限，但实际仍受容量、配额和预算约束。伸缩分为纵向伸缩和横向伸缩：纵向伸缩是调整单个实例的 CPU、内存等资源规格；横向伸缩是增加或减少应用实例数量，在云环境中更为常见。当高并发峰值过后，多余的副本和资源可以回收，避免浪费，这正是"弹性"的含义。

**可度量服务（量化服务）**指云系统对资源使用进行计量、监测和报告，为提供商和用户提供透明度，并支持按使用量计费或内部成本分摊。计量数据可以生成月度报告，作为收费依据。

云计算的本质是通过网络提供按需获取的计算、存储、网络、数据库和应用等资源，使用户能够根据业务变化快速调整资源。云计算可以提高资源利用率和交付效率，但实际成本仍取决于架构设计、使用方式和治理能力。用户可以通过 API、命令行、控制台或应用界面使用云服务；网络既可以是互联网，也可以是组织内部网络，因此私有云同样属于云计算的范畴。

### 云的部署模式

云的部署模式主要分为四种。**私有云**的云基础设施供单一组织专用，可以位于组织内部或外部，也可以由组织或第三方管理。私有云的主要动机是数据不出组织、保障数据隐私和安全。**社区云**供具有共同安全、合规或业务需求的特定组织群体专用，规模介于私有云和公有云之间。**公有云**的云基础设施面向公众开放，由云服务提供商运营，用户通过网络按需使用云资源，阿里云、腾讯云、华为云等都属于公有云。**混合云**由两个或多个独立云基础设施组成，并通过技术手段实现数据和应用的可移植、协作或统一管理。混合云在安全隐私和容灾方面有重要应用价值。企业可以将隐私数据存储在私有云中处理，将非关键数据放在公有云上，从而在成本和安全之间取得平衡；这需要在两个云环境之间进行数据同步和交互，需要相应的工具和方案支撑。

### IaaS：基础设施即服务

计算、网络和存储等资源通常称为基础设施。通过网络向用户提供这些资源能力的云服务模式称为基础设施即服务（IaaS）。IaaS 通过资源池和调度系统动态管理计算、网络和存储资源。提供商负责物理基础设施和虚拟化层，用户通常负责 Guest OS、运行时、应用和数据。以阿里云为典型例子：用户租用虚拟机时，可以选择 CPU 核数、内存大小、磁盘空间和网络带宽，平台会自动为其分配一台已安装好操作系统（如 CentOS、openEuler 等）的虚拟机；操作系统之上的应用、数据库和中间件仍需用户自行安装配置。

当前算力租赁已成为 IaaS 的重要应用形式。一些公司专门采购大量 GPU 卡形成算力集群，以租赁方式提供给需要训练或推理任务的用户。上海有青浦和临港两个主要算力中心，其中临港侧重算力出海，通过海底光缆连接日本、美国等地区。国家层面推动"东数西算"工程，在广西、内蒙古等电价较低、能源充沛的地区建设算力中心，将东部算力需求传输到西部处理。老师在此特别指出，AI 时代的竞争最终可能归结为能源竞争——堆叠再多的计算卡，如果电力供应不足，算力也无从发挥，因此能源账是算力经济的核心问题之一。

IaaS 的主要功能包括五个方面。**资源接入与抽象**通过虚拟化和软件定义等方式，将底层计算、存储和网络资源接入并组织为可管理的资源池。"软件定义"的理念是将原本无法通过软件直接操控的物理对象，改造为可以通过指令和接口进行调用、配置和管理的对象。从最早的软件定义网络（SDN）开始，逐步发展到软件定义一切（SDX）。老师以咖啡机为例解释了软件定义的具体做法：对于不可联网的设备，可以通过机器人流程自动化（RPA）技术录制手机 App 上的操作流程，将人工点击操作转化为自动化脚本，再通过软件接口调用该脚本，实现软件化操控。随着大模型的发展，GUI Agent 技术可以自动理解应用界面并执行操作路径，替代人工录制的过程。**资源分配与调度**根据容量、策略、配额以及不同租户的需求，由云控制平面选择并分配资源。**实例生命周期管理**支持虚拟机或实例的创建、启动、停止、重建和删除等操作。**云平台管理维护**支持云平台的配置、监控、运维、审计和故障处理。**用户交互与 API**为管理员和普通租户提供控制台、命令行或 API 等操作方式。

IaaS 的架构自下而上分为四层：物理资源层包含各类计算设备（x86、ARM、GPU 服务器）、存储设备（分布式存储服务器、FC-SAN 存储服务器）和网络设备（交换机、路由器、物理防火墙）；虚拟化资源层将物理资源抽象为计算、存储和网络逻辑资源，包括块存储、对象存储、文件存储、私有网络、负载均衡和虚拟机服务等；云服务控制层提供资源池管理、弹性伸缩、多租户隔离和自动化部署等能力；云管理层包含安全层、运维层、多云异构纳管、混合云管理、监控告警和认证审计等治理能力。

### PaaS：平台即服务

PaaS 在基础设施之上提供应用运行环境、开发部署工具以及可绑定的数据库、消息等平台服务。用户主要部署和管理应用及其数据，平台负责底层基础设施、操作系统和运行环境，使用户能够更专注于应用开发。对比 IaaS 和 PaaS：使用 IaaS 时，用户需要自行维护 Guest OS、中间件、运行时和应用；而使用 PaaS 时，用户只需在平台支持的运行环境中部署应用，通常无须直接管理底层虚拟机和操作系统。

PaaS 的核心价值在于实现关注点分离。普通应用开发者应当专注于业务逻辑，底层的操作系统、数据库、中间件等依赖环境最好由平台统一管理。这样，开发者将代码提交给 PaaS 平台后，平台可以自动完成构建、打包、部署和运行环境配置的全过程。

PaaS 的理想工作模式是：应用开发者提交代码或制品后，PaaS 完成构建、打包、部署和运行环境配置；平台还可以提供或绑定数据库、消息、日志、监控和告警等后端服务；应用仍需要显式声明、配置并正确使用这些依赖。具体而言，开发者将代码提交到 PaaS 平台的 CI/CD 流水线中，流水线自动执行构建、打包、部署和运行环境配置，同时根据应用声明的依赖关系自动提供相应的数据库、消息队列等服务。CloudFoundry 是 VMware 于 2011 年开源的 PaaS 平台，开发者可以通过 `cf push` 等命令提交应用，由平台完成构建、调度和运行。

PaaS 的几项核心功能包括**自动化部署**、**多副本管理**和**弹性伸缩**。自动化部署通过标准化运行环境和自动化流程减少环境差异和重复操作。多副本管理将同一应用运行成多个副本，分布在不同节点上；当单个实例或节点失效时，其他健康副本仍可继续提供服务，从而实现高可用。无状态应用副本不保存需要持久化的本地状态，可以较为容易地复制和伸缩；有状态服务（如数据库）的数据复制、一致性和故障恢复则需要由相应的数据系统负责。平台还需要通过健康检查、调度和流量分发来管理应用副本。弹性伸缩通过垂直伸缩（调整 CPU、内存）或水平伸缩（增减实例数量）应对业务负载变化，云环境中水平伸缩更加常见。

PaaS 的优点是交付效率高、高可用性、容量适应性强和多租户隔离性好。缺点在于部分 PaaS 平台可能通过专有 API、运行时或托管服务形成平台耦合，用户应用被绑定在特定平台上，迁移到其他 PaaS 平台的成本较高。因此选型时需要评估可移植性和退出成本。

### SaaS：软件即服务

SaaS 通过网络向最终用户提供完整的应用能力，通常包含用户界面和 API，但不等同于面向服务架构（SOA）。SOA 是将局部服务暴露出来供调用，而 SaaS 是将整个软件产品以服务方式发布，用户可以按需付费使用。SaaS 的底层可以构建在 IaaS、PaaS 或其他平台能力之上，用户通常只负责使用和配置应用，不涉及任何开发工作。

SaaS 最早的代表性商业化产品是 Salesforce.com。Salesforce 最初提供的是一款云端 CRM（客户关系管理）产品。传统企业使用 CRM 需要自购服务器、本地部署并维护，成本较高。Salesforce 将 CRM 以 SaaS 方式提供，企业通过浏览器访问，按月或按年付费即可使用，无需自行购置硬件和维护团队。同时产品由 Salesforce 持续更新迭代，用户无需关心升级维护问题。这种方式对小型企业来说远比自建团队和采购服务器划算。

然而，标准化的 SaaS 产品很快暴露出个性化需求难以满足的问题。不同企业对客户报表格式、分析方式等有不同要求。针对这一需求，Salesforce 推出了 Force.com 平台，允许用户在平台上通过配置而非编写底层代码来定制产品。这种面向终端用户的配置方式被称为低代码开发或无代码开发：低代码开发主要通过配置和界面拖拽生成大部分代码，局部可能需要编写少量代码；无代码开发则完全无需编写代码，通过自然语言描述需求即可由大模型自动生成代码和部署。Google App Engine 等早期 PaaS 产品则要求用户自行编写代码并上传，由平台完成后续的构建、编译和部署。

IaaS、PaaS 和 SaaS 描述的是不同的服务责任边界。三者并非严格的层级依赖关系，SaaS 可以直接构建在 IaaS 之上，也可以构建在 PaaS 之上。

### 云计算架构演进与发展大事件

云计算的架构演进可以大致分为四个阶段。第一阶段是服务器虚拟化，通过虚拟化技术将单台服务器划分为多个虚拟机，提高资源利用率并节省资本支出；第二阶段是单一云数据中心，在虚拟化集群之上利用 OpenStack 等管理平台实现自动化管理，提升灵活性和敏捷性；第三阶段是分布式云数据中心，通过多数据中心和多个 OpenStack 集群实现多站点服务；第四阶段是混合云，将自建云和第三方云有机结合，在成本与企业数据保护策略之间取得均衡。

云计算的发展脉络是从基础设施虚拟化到基础设施云化，再到混合云与多云管理，最终走向应用云原生化。基础设施虚拟化提高资源利用率并提供隔离环境；基础设施云化增加资源池、自助服务、调度、计量和自动化管理能力；混合云与多云管理协调多个独立云环境中的应用和数据；应用云原生化则改进应用的设计、交付、运行和治理方式。除了云平台本身技术的进步，云上的应用也需要从单体、小规模、有状态、进程式、烟囱式架构逐步向云原生应用模式转变。云原生通过自动化、声明式 API、容器与编排、Serverless、可观测性和韧性设计等方式提升交付和运行能力。

云计算发展历程中的关键事件包括：2006 年 Amazon 推出 EC2，用户可以在公有云上按需申请和管理虚拟服务器，早期 EC2 使用 Xen 虚拟化技术，这是最早的代表性 IaaS 服务；2008 年 Google 发布 Google App Engine，成为早期代表性的 PaaS 产品；2009 年 Heroku 作为早期代表性 PaaS 之一，为开发者提供应用部署和运行平台；2010 年 Microsoft Azure 正式商用，早期侧重平台服务，同年 Rackspace 和 NASA 发布 OpenStack，推动开源 IaaS 和私有云生态发展；2011 年 CloudFoundry 作为开源 PaaS 平台发布；2012 年 Google Compute Engine 发布预览，并于 2013 年正式可用，主要云服务商的 IaaS 能力进一步完善；2014 年 AWS 推出代表性的 FaaS 产品 Lambda，推动 Serverless 应用模式发展；2015 年 CNCF 成立，Kubernetes、容器和云原生开源生态进入快速发展阶段。

### 内容小结

本次课程围绕云原生技术的前置知识展开，系统介绍了虚拟化与云计算的核心概念。虚拟化的原理是在物理资源与上层软件之间引入抽象层，将物理存在的计算、存储和网络资源表示为逻辑资源。虚拟化实现机制分为全虚拟化、半虚拟化和硬件辅助虚拟化；虚拟化架构分为裸金属架构（Type 1）和宿主模式架构（Type 2）。服务器虚拟化通过 Hypervisor 在物理主机上运行多台虚拟机，虚拟机具有分区、隔离、封装和独立四个特征。虚拟化能够提高资源利用率并提供隔离环境，但缺少云管理平台时仍存在资源获取时间长、弹性不足和自动化治理不足等问题。云计算通过网络按需提供可配置计算资源池，具有按需自助、访问无边界、资源池化、极速伸缩和量化服务五大特点。云计算服务模式包括 IaaS、PaaS 和 SaaS，分别对应基础设施、平台和软件三个层次的服务责任边界。从服务器虚拟化到云原生化，云计算的发展呈现出资源利用率和自动化管理能力不断提升、应用交付和运行模式不断优化的趋势。下一节课将正式进入 Docker 容器技术的讲解。
