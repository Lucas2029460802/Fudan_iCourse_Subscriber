### 进程控制块
#### 进程控制块的定义与核心价值
操作系统的主要职责之一是管理系统中并发的多个进程。为了实现这种管理，操作系统必须为每一个进程维护一个数据结构，用来记录进程的关键信息，例如其身份标识、执行状态和资源使用情况。这个数据结构被称为**进程控制块**（Process Control Block，简称 PCB），在某些语境下也被称作**进程描述符**（Process Descriptor）。PCB 是进程在操作系统中存在的唯一标志，也是操作系统对进程进行全生命周期管理（包括创建、调度、暂停和终止）的核心依据。可以认为，操作系统对进程的大部分管理工作，本质上都是通过对 PCB 的操作来完成的。

操作系统通过维护一张**进程表**（Process Table）来组织所有 PCB。这张表通常是一个结构体数组，数组的每一个条目对应一个进程的 PCB。每个进程都有一个全局唯一的标识符，即**进程标识符**（Process Identifier，简称 PID）。通过 PID 和进程表，操作系统可以快速找到并访问任意一个进程的 PCB，从而获取或更新该进程的所有关键信息。

#### PCB 中的信息组织
存储在 PCB 中的信息虽然复杂，但通常可以被归纳为三大类。这个分类并非是唯一的标准，但可以提供一个清晰的框架来理解 PCB 的构成。

##### 进程标识信息
这部分信息相对简单，主要用于系统的识别和权限管理。

-   **进程ID (PID)**
    进程的唯一的数字身份标识，是操作系统调度和管理进程的核心索引。

-   **父进程ID (PPID)**
    标识了创建本进程的父进程，用于构建系统的进程树结构，维护父子进程间的生命周期关联。

-   **用户ID / 组ID (UID / GID)**
    定义了进程归属于哪个用户和用户组，并以此确定进程对系统资源的访问权限边界。操作系统通过 UID/GID 来判定一个进程是否有权访问某个文件或执行某项操作。

##### 处理器状态信息
这部分信息是 PCB 的核心，主要用于保存和恢复 CPU 的状态，从而支持多个进程的并发执行。在多道程序系统中，一个正在运行的进程可能会因为时间片耗尽等原因被操作系统剥夺 CPU 的使用权。为了确保该进程在未来某个时刻能够从被中断的位置无缝地继续执行，操作系统必须在其被挂起时，将 CPU 中几乎所有寄存器的当前值（即“上下文”或“处理器状态”）保存到该进程的 PCB 中。这些寄存器包括：

-   **程序计数器 (Program Counter)**
    指向进程下一条将要执行的指令地址。

-   **通用寄存器**
    保存函数执行的中间结果和临时数据。

-   **栈指针 (Stack Pointer)**
    指向当前函数调用栈的顶部。

-   **状态字寄存器 (Processor Status Word)**
    包含条件码（如进位、零标志）和 CPU 的当前执行模式（内核态/用户态）等信息。

当操作系统决定恢复执行该进程时，会将 PCB 中保存的处理器状态信息重新加载回 CPU 的各个寄存器中。这个“保存-恢复”机制是实现 CPU 虚拟化的技术基础，它让多个进程看起来像是在同时共享一个物理 CPU。

以下是进程切换时保存和恢复处理器状态的示意图：

-   **进程切换前**
    -   CPU 中运行进程 A， 寄存器组（PC、寄存器等）反映了进程 A 的执行状态。
    -   PCB_A 中存储的是之前被保存的状态。
    -   PCB_B 存储的是进程 B 的完整状态，其中程序计数器指向它上次中断时的位置。

-   **进程切换过程**
    1.  **保存状态** —— 将当前 CPU 中属于进程 A 的所有寄存器值，保存到 PCB_A 的相应字段中。
    2.  **恢复状态** —— 从进程 B 的 PCB_B 中，取出其保存的处理器状态，并将其加载到 CPU 的各个寄存器中。

-   **进程切换后**
    CPU 继续运行，但此时执行的是进程 B，程序计数器也指向进程 B 下一条将要执行的指令地址。处理器状态信息就如同进程执行过程中的一份完整“快照”，是进程在 CPU 上恢复执行的唯一依据。

##### 进程控制信息
这是一个包罗万象的类别，包含了除上述两类信息之外，操作系统管理和控制进程所需要的所有其他信息。这些信息为调度、资源分配、通信和保护提供了决策支撑。

-   **调度和状态信息**
    这是操作系统执行调度功能的核心依据。主要包括：

    -   **进程状态 (Process State)**
        记录进程当前处于运行态（Running）、就绪态（Ready）还是阻塞态（Blocked）等状态。

    -   **优先级 (Priority)**
        描述了进程的调度优先级，高优先级的进程会被优先分配 CPU 资源。不同优先级可能对应不同的就绪队列。

    -   **调度相关信息 (Scheduling-related Information)**
        这部分信息取决于具体的调度算法。例如，在轮转调度（Round Robin）中，会记录进程已经等待的时间和在上一轮执行中消耗的时间；在最短进程优先（SPN）算法中，则需要记录预期的执行时间。

    -   **等待事件 (Event)**
        如果进程处于阻塞态，则记录它所等待的事件标识（例如某个 I/O 操作的完成或某个锁的释放）。

    -   **数据结构化信息 (Data Structuring)**
        进程之间并非孤立存在。一个进程可以创建子进程，从而形成父子关系，构成一个进程树。此外，处于相同状态的进程（如所有就绪进程）会被链接成一个队列。因此，PCB 中需要包含指向父进程、子进程的指针，以及用于组织队列的前后指针。

-   **内存管理信息**
    记录进程的虚拟地址空间到物理内存的映射关系。这取决于操作系统所采用的内存管理方案。对于采用分页（Paging）或分段（Segmentation）的系统，PCB 中会包含指向该进程的页表（Page Table）或段表（Segment Table）的指针。

-   **资源拥有与文件 I/O 信息**
    记录了进程所拥有的资源，特别是它打开的文件。每个进程在创建时通常会默认打开三个文件：标准输入（stdin，通常是键盘）、标准输出（stdout，通常是显示器）和标准错误（stderr，通常也是显示器）。PCB 中会包含一个指向**文件描述符表**（File Descriptor Table）的指针，该表记录了进程所有打开的文件的相关信息。

-   **记账信息 (Accounting Information)**
    记录进程对处理器时间和其他资源的使用历史，例如 CPU 累计执行时间、内存使用峰值等。这些信息可以用于系统性能分析、资源计费或调度决策。

### 进程控制
进程控制涉及到操作系统对进程生命周期的直接干预和管理，主要包括进程的创建与终止，以及支撑这些操作的低层机制——模式切换。

#### 进程的创建与终止
一个进程的存在是动态的，它有创建、执行和消亡的过程。

**进程创建**主要发生在以下几种场景：新的批处理作业被提交、用户交互式登录、操作系统为提供服务而创建新进程（如打印服务），以及由现有进程通过系统调用主动创建子进程。

在 Unix/Linux 系统中，创建一个新进程是一个多步的过程，最终将一个静态的可执行程序转换为一个动态运行的实体。其核心步骤如下：

1.  **加载代码和静态数据**
    操作系统将存储在磁盘上的可执行文件中的代码段（Code Segment）和已初始化数据段（Data Segment）加载到进程的虚拟地址空间中。

2.  **分配栈（Stack）空间**
    栈用于支持函数调用。当进程第一次进行函数调用时，操作系统会为其分配栈空间。后续每次函数调用，都会在栈上分配一个“栈帧”（Stack Frame），用于存储该函数的局部变量、参数和返回地址，这是由系统隐式自动完成的。

3.  **分配堆（Heap）空间**
    堆是用于显式请求的动态内存分配的区域。例如，在 C/C++ 中使用 `malloc` 或在 Java 中使用 `new` 关键字创建的对象，其内存便是在堆上分配的。

4.  **I/O 相关初始化**
    执行一些与 I/O 相关的初始化任务。例如，在 Unix 系统中，新创建的进程会默认继承或打开三个文件描述符，即标准输入（0）、标准输出（1）和标准错误（2）。

5.  **跳转到入口点执行**
    完成所有初始化工作后，CPU 将跳转到程序的入口点（如 C 语言的 `main` 函数），进程正式开始执行。

**进程终止**发生在进程执行完最后一条语句并要求操作系统将其删除时。进程可以主动调用 `exit()` 系统调用，并返回一个状态值给其父进程。父进程则可以通过 `wait()` 系统调用来获取该状态值。操作系统在进程终止时，会回收分配给它的所有资源，包括物理和虚拟内存、打开的文件句柄以及 I/O 缓冲区等。此外，一个进程（通常是父进程）也可以通过系统调用强制终止另一个进程。

#### Unix 系统中的 `fork()` 与 `exec()` 分离设计
Unix 系统在进程创建上有一个独特的设计哲学：将**派生新进程**和**执行新程序**这两个动作分离开，分别由 `fork()` 和 `exec()` 系列系统调用完成。

-   `fork()`
    被调用时，它会创建一个与当前进程（父进程）几乎完全相同的副本，即子进程。子进程拥有父进程代码段、数据段、堆栈和打开文件的独立副本。`fork()` 调用一次，但会有两个返回值：在父进程中返回新创建的子进程的 PID（大于0），在子进程中返回 0。通过判断返回值，程序可以区分自己是在父进程还是子进程中运行，并执行不同的代码分支。

-   `exec()` 系列
    该系列调用（如 `execlp`, `execvp`）会在**不创建新进程**的前提下，用一个全新的程序镜像完全替换当前进程的地址空间。代码段、数据段、堆栈等所有内容都会被新的程序所取代，进程的 PID 保持不变，但执行的程序已完全不同。

这种分离设计的目的在于提供极大的灵活性，尤其是在构建 Unix Shell 时。Shell 在 `fork()` 和 `exec()` 之间，可以对子进程的 I/O 环境进行一系列定制化操作，从而轻松实现输出重定向和管道等高级功能。

-   **输出重定向**
    对于命令 `wc p3.c > newfile.txt`，Shell 的处理流程是：
    1.  调用 `fork()` 创建一个子进程。
    2.  在子进程中，关闭其标准输出（文件描述符 1）。
    3.  然后，打开（或创建）文件 `newfile.txt`，由于 Linux 系统中内核总是使用当前可用的最小文件描述符，因此新打开的文件会被分配文件描述符 1。
    4.  至此，子进程的标准输出被巧妙地重定向到了文件 `newfile.txt`。
    5.  最后，调用 `execlp(“wc”, “wc”, “p3.c”, NULL)` 来执行 `wc` 程序。`wc` 程序的代码依然是向文件描述符 1（标准输出）写入，但此时它实际上写入的是 `newfile.txt` 文件。

-   **管道机制**
    对于命令 `grep -o foo file | wc -l`，Shell 的处理流程如下：
    1.  调用 `pipe()` 系统调用，创建一个内核缓冲区（管道），该管道有两个端：一个读端和一个写端，分别由两个文件描述符表示。
    2.  调用 `fork()` 创建第一个子进程，用于执行 `grep`。该子进程关闭管道的**读端**，并将自己的标准输出（文件描述符 1）重定向到管道的**写端**。然后调用 `exec()` 执行 `grep` 命令。这样一来，`grep` 的所有输出都写入了管道。
    3.  再次调用 `fork()` 创建第二个子进程，用于执行 `wc -l`。该子进程关闭管道的**写端**，并将自己的标准输入（文件描述符 0）重定向到管道的**读端**。然后调用 `exec()` 执行 `wc -l` 命令。这样一来，`wc -l` 将从管道中读取第一个命令的输出作为自己的输入。

### 执行模式与模式切换
为了确保操作系统的稳定与安全，现代 CPU 至少提供了两种不同的特权级执行环境。

#### 用户态与内核态
这两种执行模式构成了系统保护的基础。

-   **用户态 (User Mode)**
    权限较低。用户的应用程序代码在此模式下运行。处于用户态的代码只能访问自己的地址空间，并且无法执行那些可能危及系统安全的**特权指令**，例如直接操作 I/O 设备、修改处理器状态寄存器或访问其他进程的内存区域。

-   **内核态 (Kernel Mode)**
    亦称“系统态”或“监管态”，权限最高。操作系统的内核代码在此模式下运行。在内核态下，代码可以访问所有内存区域、执行所有指令（包括特权指令），并对硬件资源拥有完全的控制权。

系统启动时，CPU 处于内核态，因为引导程序（Bootstrap）和操作系统需要初始化整个系统。当操作系统准备运行第一个用户程序时，它会通过一条特权指令将 CPU 切换到用户态。**任何试图在用户态下执行改变 CPU 状态的指令，都会被硬件阻止。** 整个系统运行期间，CPU 在内核态和用户态之间的切换是受到严格控制的，只有三种明确的事件发生时才可能发生，这保证了内核不会因用户程序的错误而崩溃。

#### 模式切换的五步流程
当一个应用程序因系统调用、异常或硬件中断等原因，需要从用户态切换到内核态时，CPU 和操作系统会协同完成一次**模式切换**。其标准流程如下：

1.  **保护现场 (Save Context)**
    CPU 自动将用户态的关键寄存器的值（如程序计数器、栈指针等）压入该进程的**内核栈**中。这是为了在执行完内核代码后，能够准确地恢复现场并回退到用户态继续执行。请注意，这里保存的寄存器数量远少于一次完整的进程上下文切换。

2.  **权限升级 (Privilege Escalation)**
    CPU 的特权级从用户态（低特权级）切换到内核态（高特权级），至此，CPU 获得访问所有硬件资源和内存区域的完整权限，为执行内核代码做好准备。

3.  **内核执行 (Kernel Execution)**
    根据引发模式切换的原因（系统调用号、中断向量号），CPU 跳转到相应的内核处理程序（系统调用处理程序、中断处理程序、异常处理程序），并执行具体的系统功能，例如完成磁盘 I/O 请求、处理缺页异常或进行进程调度。

4.  **恢复现场 (Restore Context)**
    内核功能执行完毕后，从该进程的内核栈中弹出先前保存的用户态寄存器的值，将其恢复至 CPU 的各个寄存器中，为返回用户态做好准备。

5.  **权限回落 (Privilege De-escalation)**
    CPU 特权级从内核态切换回用户态。此后，CPU 从被中断的断点处继续执行用户程序的后续指令。

整个模式切换的本质，是在同一个进程的“用户栈”和“内核栈”之间进行一次轻量级的上下文转换。它的额外开销显著低于进程切换，因为它不改变当前运行的进程或线程，虚拟地址空间保持不变，TLB（快表）也无需刷新。

#### 触发模式切换的三类事件
严格来说，只有在以下三种情况下，CPU 才会从用户态陷入内核态，操作系统也才能重新获得控制权。

1.  **系统调用 (System Calls)**
    用户程序主动、显式地发起服务请求，例如请求文件读写（`read`/`write`）、进程创建（`fork`）等。应用程序通过执行一条特殊的软中断指令，主动将控制权移交给操作系统，以使用其提供的服务。

2.  **陷阱 (Traps)**
    由当前正在运行的进程**自身**产生的错误或异常条件所引发，是一种**同步**事件。典型例子包括：
    -   **除零错误 (Divide by Zero)**
        试图用零作为除数。
    -   **缺页异常 (Page Fault)**
        访问的虚拟地址所在的页面当前不在物理内存中。
    -   **非法指令 (Illegal Instruction)**
        试图执行一条特权指令或无效的机器指令。
    这些错误发生时，CPU 硬件会立即检测到，并强制引发一个陷阱，迫使控制权进入内核态，由操作系统的异常处理程序来决定如何处理（如杀死进程、加载缺页等）。

3.  **硬件中断 (Hardware Interrupts)**
    由**当前正在运行的进程之外**的硬件设备产生的信号，是一种**异步**事件。典型例子包括：
    -   **时钟中断 (Timer Interrupt)**
        由可编程间隔定时器产生，用于通知操作系统进行时间片轮转调度。
    -   **I/O 中断 (I/O Interrupt)**
        例如键盘有按键按下、硬盘数据传输完成、网卡收到数据包等。
    硬件中断会强制打断当前进程的执行，转入内核态的中断处理程序。

### 上下文切换
**上下文切换 (Context Switch)** 是指操作系统将 CPU 的控制权从一个正在运行的进程（或线程）转移到另一个进程（或线程）的过程。它通过“保存当前执行实体的状态，并恢复另一执行实体的状态”来实现。上下文切换是**多任务操作系统最核心的特征**，它允许多个进程或线程共享单个 CPU。

与模式切换不同，上下文切换会导致当前正在运行的进程或线程发生改变。其开销主要分为两类：

-   **进程切换**
    发生在两个不同进程之间。这是开销最高的一种切换。它不仅要保存和恢复大量的 CPU 寄存器，**关键开销在于必须完成地址空间的切换**。
    由于新旧进程拥有独立的虚拟地址空间，这会导致：
    1.  **内存管理数据结构更新**
        操作系统需要将 CPU 的页表基址寄存器（如 CR3）指向新进程的页表。
    2.  **TLB 刷新**
        TLB 是用于加速虚拟地址到物理地址转换的硬件缓存。地址空间切换后，TLB 中缓存的旧进程的地址映射全部无效，新进程初始执行时会频繁出现 TLB 未命中，导致性能显著下降。
    3.  **CPU 高速缓存污染**
        进程切换后，CPU 高速缓存中大部分是旧进程的数据，新进程一开始会遭遇大量的缓存未命中，同样导致性能下降。

-   **线程切换**
    发生在同一进程的两个线程之间。其开销远低于进程切换。因为同一进程内的所有线程共享相同的虚拟地址空间，因此**无需切换地址空间**。
    1.  页表基址寄存器无需更改。
    2.  TLB 无需刷新，其缓存的映射关系依然有效。
    3.  CPU 高速缓存中的数据也有很大一部分可以被新线程直接利用，局部性得以保持。
    线程切换只需要保存和恢复线程独有的资源，如程序计数器、寄存器和栈。

模式切换、线程切换和进程切换的对比可以总结如下：

| | **模式切换** | **线程切换** | **进程切换** |
| :--- | :--- | :--- | :--- |
| **地址空间变化** | 无 | 无 | **有** |
| **TLB 刷新** | 不需要 | 不需要 | **需要** |
| **典型触发事件** | 系统调用、中断、异常 | 时间片耗尽、一个线程等待 I/O 或主动让出 CPU | 同上，发生在不同进程的两个线程间 |
| **相对额外开销** | 低 | 较低 | **高** |

### 线程的引入
#### 从单线程进程到多线程进程
传统的“经典进程”模型存在一个基本假设：每个进程只拥有单一的**控制线程**。这意味着在任何一个时刻，一个进程只能执行一项任务。进程作为一个实体，同时扮演了两个角色：
1.  **资源拥有者**
    进程被分配了独立的虚拟地址空间以存放进程映像，并拥有 I/O 设备、文件等资源。
2.  **调度执行单元**
    进程拥有一条单一的执行路径，被 CPU 作为一个整体来调度、分派和切换。

在当代操作系统中，这两个角色被分离开。**资源拥有的单元仍然被称为进程，而 CPU 调度和分派的基本单元则被称为线程 (Thread)**，或“轻量级进程”。这种方法被称为多线程模型。一个进程因此可以拥有多个控制线程。

在单线程进程模型中，进程映像包含代码段、数据段、堆、文件等资源，以及一个唯一的栈和一个唯一的线程执行路径。而在多线程进程模型中，进程仍然维护代码段、数据段、堆等共享资源，但内部拥有多个线程。每个线程都拥有自己**独立的程序计数器、寄存器组和栈空间**，但与其他线程共享进程的代码段、数据段、堆空间以及打开的文件等操作系统资源。这意味着，同一个进程内的多个线程可以非常容易和高效地进行通信，因为它们可以直接读写共享内存中的全局变量，而无需任何系统调用。

从地址空间的布局来看，多线程进程与单线程进程最关键的区别在于**栈**。一个拥有 $n$ 个线程的进程，其地址空间中会存在 $n$ 个独立的栈，每个栈对应一个线程的函数调用序列。同时，每个线程也有自己独立的程序计数器，指向各自执行序列中的下一条指令。

#### 多线程架构的优势
相比于多进程模型，在应用程序中使用多线程编程可以带来四个主要优势：

1.  **响应性**
    在交互式应用中尤其重要。可以将界面交互放在一个主线程，而将耗时计算或阻塞式 I/O 操作放在后台线程。这样，即使后台任务被阻塞，主线程依然能及时响应用户的操作，避免程序界面出现“假死”状态。

2.  **资源共享**
    进程的线程天生共享该进程的所有内存和资源。这种共享使得线程间的通信（IPC）变得极为便捷，完全不需要经过内核，性能极高。

3.  **经济性**
    与进程相比，线程的创建、终止和上下文切换都更加经济高效。创建一个线程所需的时间和内存开销远低于创建一个进程。同样，同一进程内两个线程之间的切换，由于不涉及地址空间切换，其开销也远低于进程切换。

4.  **可扩展性——利用多处理器架构**
    在多核或多处理器系统中，同一进程的多个线程可以被调度到不同的处理器核心上**并行**执行，从而真正意义上地加速单个应用程序的运行。对于单处理器系统，多线程也可以将 I/O 操作和计算任务重叠，实现并发执行。

需要特别强调的是，**进程是操作系统提供保护的基本单位**。操作系统负责将一个进程与另一个进程隔离开，防止相互干扰。而对于同一个进程内部的多个线程，操作系统默认是不提供保护的。线程间的数据安全与协同工作需要由应用程序开发者在用户态自行负责，即通过后续章节将介绍的线程同步机制来保证。

#### 多线程环境的分类
根据系统支持的地址空间数量和每个地址空间内的线程数量，可以将计算环境分为四类：

-   **单进程单线程**
    例如传统的 MS-DOS 操作系统。系统只有一个地址空间，且其中只有一个执行线程。

-   **单进程多线程**
    例如一个 Java 运行时环境（JVM）的实例。一个 JVM 进程内部可以运行多个 Java 线程（如垃圾回收线程、事件分发线程等）。

-   **多进程单线程**
    例如传统的 Unix 系统早期版本。系统可以运行多个进程，但每个进程内部只有一个线程。

-   **多进程多线程**
    例如当代主流的 Windows, Linux, Solaris 等操作系统。系统支持多个并发进程，且每个进程内部又可以拥有多个线程。

选择何种结构来解决问题，依赖于任务的性质。如果任务之间彼此独立，使用多个单线程的进程更为稳定，因为一个进程的崩溃不会影响其他进程。如果任务之间耦合度高，需要频繁和高效的通信与数据共享，则使用单一进程内的多线程更为合适。

### 线程模型：用户级与内核级
线程的实现主要有两种基本模型：**用户级线程（ULT）**和**内核级线程（KLT）**，它们的核心区别在于线程管理的职责归于谁。

#### 用户级线程 (ULT)
在纯用户级线程模型中，所有的线程管理工作都由**应用程序**通过一个处在用户空间的**线程库（Thread Library）**来完成。内核完全不知道线程的存在，它看到的依然是传统的单线程进程。线程库提供创建、销毁、调度以及保存和恢复线程上下文的全部功能。

**ULT 的优点：**

-   **线程切换开销极小**
        完全在用户空间完成，无需进行代价高昂的模式切换到内核态。
-   **调度策略可定制**
        应用程序可以根据自身需求，设计和使用最适合的调度算法。例如，一个网络服务器可以使用自定义的协作式调度，而非操作系统内核的抢占式调度。
-   **操作系统无关性**
        可以运行在任何不支持内核级线程的操作系统上。

**ULT 的缺点（可通过一个例子来深刻理解）：**

假设进程 `B` 内部包含两个用户级线程：线程 1（就绪）和线程 2（运行）。在操作系统眼中，进程 `B` 正在运行。我们来分析三种事件对状态的影响：

1.  **线程 2 执行了一次阻塞式系统调用**
    例如请求从磁盘读取数据。由于内核只看得见进程 `B`，它会将这个系统调用视作整个进程的阻塞请求。内核随即会将进程 `B` 的状态从**运行态**切换为**阻塞态**，并将 CPU 分配给其他进程。
    尽管在逻辑上，线程 1 仍然可以继续运行，但实际上，由于整个进程 `B` 都陷入了阻塞，线程 1 也永远无法获得 CPU。这暴露了 ULT 的第一个严重缺陷：**一个线程的阻塞会导致整个进程内的所有线程都被阻塞。**

2.  **一个时钟中断到达，内核认为进程 B 的时间片已耗尽**
    内核会将进程 `B` 的状态从**运行态**切换为**就绪态**，并将其放入就绪队列。此时，线程 2 在应用程序看来仍然是运行的，但它的指令实际上已经停止在 CPU 上执行了。在这个场景下，**ULT 的“运行”状态并不代表指令正在 CPU 上执行；真正执行的前提是其所在的进程必须正在运行。**

3.  **线程 2 需要等待线程 1 完成某项工作**
    这是同一个进程内部的线程同步问题。线程 2 可以通过调用线程库提供的某个函数来将自己置为**阻塞态**，并将线程 1 从**就绪态**切换为**运行态**。这一切换完全在用户空间完成，不涉及内核，效率非常高。线程 2 的阻塞不会影响到进程 `B`，进程 `B` 仍然处于运行态。

    ULT 的其他一些主要缺点还有：
    
-   **无法利用多核处理器**
    因为内核只看到了一个进程/一个线程，所以无论如何都无法将同一个进程的多个 ULT 调度到不同的 CPU 核心上实现真正的并行。
-   **缺页异常问题**
    与阻塞式系统调用类似，如果一个线程触发了缺页异常，整个进程（以及它内部的所有线程）都会被阻塞。

#### 内核级线程 (KLT)
在纯内核级线程模型中，所有线程的创建、调度和管理工作都由**操作系统内核**完成。内核会为整个系统维护一张全局的线程表，并像调度进程一样调度线程。应用程序则通过标准的系统调用接口来使用内核级线程。

**KLT 的优点：**

-   **真正的并行性**
    内核可以将同一个进程内的多个 KLT 调度到多个处理器核心上同时运行，从而充分利用多核系统的计算能力。

-   **单个线程阻塞不影响其他线程**
    如果进程中的一个执行了阻塞式系统调用，内核只会阻塞这一个特定的线程，并可以立即从该进程的就绪队列中调度另一个线程继续执行。这克服了 ULT 模型最大的缺陷。

-   **内核本身也可以是多线程的**
    操作系统内核自身的服务程序也可以通过多线程来提升性能和响应能力。

**KLT 的缺点：**

-   **同一进程内的线程切换开销大**
    任何线程的控制权转移，即使是同一进程内的两个线程之间，也都必须经过**模式切换**，陷入内核态来完成。这比 ULT 在用户空间的切换慢得多。

#### ULT 与 KLT 的映射关系
在许多现代操作系统中，ULT 和 KLT 不是孤立的，而是可以组合使用的，它们之间存在多种映射关系，提供了不同的折衷方案。

-   **多对一模型**
    多个 ULT 映射到**一个** KLT 上。这相当于纯 ULT 模型的实现。其优缺点与纯 ULT 完全一致。

-   **一对一模型**
    每个 ULT 映射到**一个** KLT 上。这相当于纯 KLT 模型的实现。其优缺点与纯 KLT 完全一致。

-   **多对多模型**
    将多个 ULT 多路复用到一个较小数量或相等数量的 KLT 上。这是一种更灵活的折衷方案。它既能让程序员创建任意数量的 ULT，又能通过合理地设置 KLT 池的数量来利用多核处理器的并行性，并在有线程执行阻塞系统调用时，将其他 ULT 调度到另外的 KLT 上执行，而不会阻塞整个进程。不过，这种模型的实现技术也最为复杂。
